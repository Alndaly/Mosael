A workflow is **done once, run endlessly**: it turns something you did once into a process that runs again on new input, runs unattended, and runs at scale. Start-node inputs and templates make it reusable; it can carry media through the timeline, subtitles, export and publishing to a finished piece; loops, concurrency and branches handle batches and say which item failed; schedules, webhooks, the agent or other workflows can start it; and every run keeps each node's inputs, results and errors. The process itself is the product. While you are still looking, revising and picking between versions, use a [creative board](/docs/guides/boards).

Workflows connect media, models and tools into reusable steps. Configure node inputs and run the readiness check before starting a flow. Use schedules or webhooks for recurring work. Run history keeps node inputs, results and errors available for inspection.

## Download and import official templates

The [website workflow catalog](/workflows) describes every official template, what it needs, and offers Chinese and English downloads; the template gallery in the app can add them directly too.

1. Download a `.mosael-workflow.json` file; no extraction is needed.
2. Choose your workspace in the app, open Workflows, then use Import workflow to select the file.
3. Open the imported graph, choose your own providers and models, fill in the start node's required parameters and pass the readiness check before running.

Downloads contain no account secrets or private assets, and do not automatically select local default models. Importing needs 1.8.3 or newer. Node names follow the language of the file you downloaded.

| For | Templates |
| --- | --- |
| Finished videos | **Topic to finished video** (brief → script and visual bible → characters looked up in the asset library first, with turnarounds / location art drawn and saved only for new ones → storyboard → an automatic 3D blockout → per-shot video from the blockout → narration captions → export; the most expensive one, up to 8 shots by default), **Long video into vertical clips** (picks up to 12 segments, each on its own vertical timeline with short captions) |
| Clean-up and montage | **Transcript-based video cleanup** (denoise first, then cut pauses, fillers and repetition by the transcript; for material up to about 30 minutes), **Montage from your own footage** (orders a tagged batch of your clips and adds narration and captions) |
| Translated dubbing | **Translated dubbing with subtitles** (transcribe, translate and subtitle line by line on the original timecodes, dub each line into its slot, strip the original voice but keep the music), **Translated dubbing with lip-sync** (the same, then the speaker's lips follow the dub) |
| Products and business | **Product photo into on-model shots**, **Product into a narrated short**, **Fabric into applications and a spec sheet** |
| Digital humans | **Script into a talking-head video**, **Product into a presenter-led short** (see [Digital humans](/docs/guides/digital-humans)) |
| Analytics | **Social account health check**, **Why a video went viral**, **Comment insights and audience** (see "Analytics templates" below) |

What each one needs (a chat model, an image model that takes references, a video model, a cloned voice, a transcription or separation engine…) is on its card, and the template gallery checks each item off.
The reduce-noise node uses the built-in engine by default. For speech-led material with messy noise (keyboards, dishes, chatter)
switch it to DeepFilterNet (a deployment admin downloads it first under Admin → Engines); it removes music as well.

- **Edges** define execution order; drag from a node's right port to a downstream node's left port. The toolbar switches **edge shape** between curved (bezier) and stepped (right-angle); your choice is remembered.
- Click a node to open its **inspector** — it sits **directly below** the node, and a floating bar sits
  **directly above** it: content sections on the left (**Parameters** / **Advanced** / **Outputs**, plus
  **This run** once it has run — each shown **only when the node has it**), node actions on the right
  (open subgraph, delete). "Advanced" holds the knobs that **work fine left blank**, so the first screen
  isn't a wall of sampling parameters.

### The start node: parameters, required and options

The start node's parameters are a three-column table — **Name / Default / Required** — and **Add** appends a row.

![The start node’s parameter table: name / default / required, and Add](/media/screens/en/workflow-start-params.png)

- **Each row has its own Required checkbox.** A required parameter without a default must be filled in at run time; until it is, the
  run won't start — placeholder examples are never taken for real input.
- **Option parameters**: the Default cell becomes a dropdown (**Pick one**) limited to the given options. An option whose prerequisite
  isn't set up is marked "not set up" but can still be picked; the run then says what's missing (that's how the analytics templates'
  data source works).
- **The start node has one output port per parameter**, so downstream nodes wire straight from the matching port.
- References to parameters the start node doesn't declare, defaults outside the options, empty or duplicate names are all flagged by
  the readiness check.

![An options parameter: the analytics template’s data_source is a dropdown with Built-in browser and “TikHub · not ready”](/media/screens/en/workflow-start-options.png)

### Loops and branches

- The **Condition** node has true / false outlets. A node hanging off one outlet runs only when that branch holds; a data connection it
  takes a value from elsewhere decides only the value, never whether it runs. When the condition's **Left value** comes from upstream,
  the canvas draws its input port. Empty lists and objects count as empty, and two numbers compare numerically.
- **Loop · for each** runs one item after another by default. When items don't depend on each other (such as generating each shot),
  raise **Concurrency** to 2–4 under Advanced; results keep their original order. **Max items** caps the list; **When an item fails**
  is either **Fail the whole loop** (the default: once any item fails **no new item starts**, items already running finish and their
  submitted generations are still collected) or **Note it and carry on** — the failures are listed under **Failed items** and in the
  notification. Without an iteration output, each item returns everything that round produced plus the item itself (`loop.item`).
- **Loop · while** stops after 50 rounds by default (adjustable, at most 1000).
- **Split into batches** divides a list into fixed-size, non-overlapping batches in the original order, ready for a for-each loop. Use it for comments and other long result sets instead of putting the entire list into one model call; it also outputs batch count and original item count.
- **Text to speech and Dub subtitles** ask for the engine first, then the voice: with "Cloned voice" the voice list is your
  voice library; pick an engine and the list becomes that engine's voices. Changing the engine clears the chosen voice.

### Top toolbar

The order matches creative boards: add and undo/redo, comments, markers and their list, search and view controls, then the AI assistant. Readiness, run history and Run form a separate group on the right.

**More** contains rename, revision history, file export and deletion. The current version shows at the end of the revision-history row; deletion sits in its own group and still requires confirmation. Arrow keys move through the menu and Escape closes it. ⌘F finds nodes across the whole graph (ids too): matches are outlined on the canvas and Enter / ⇧Enter steps through them. ⌘S saves and ⌘Enter runs. In narrow windows, arrows reveal the remaining tools while the assistant, run controls and More stay visible.

### When something is buried

With dense nodes or stacked floating panels, select one and press **⌘/Ctrl + ]** to raise it or
**⌘/Ctrl + [** to send it down. Floating panels use the same pair, but **nodes can never cover a
floating panel** — otherwise the inspector would end up buried under the very node it's editing.

Node forms use a translucent, blurred surface above the canvas. When an assistant panel is open, selecting a node centers it in the unobscured canvas area. Media nodes have compact previews that open a larger player.

## Variables and references: wiring upstream outputs into downstream inputs

After a node runs it writes results into the context, and downstream fields read them with references such as `{{nodeId.output}}`.
**The interface doesn't show raw `{{…}}`**: in parameters, the prompt editor, stale-reference notices and the readiness check, a
reference reads "**Node title · output · field**"; one that points nowhere turns red and says why — the node can't be found (deleted,
renamed or mistyped) or it has no such output — so you can pick another upstream output.

![References in a text template render as “node title · output” tags instead of raw double-brace references](/media/screens/en/workflow-reference-tags.png)

Data ports match properties one for one: named configuration inputs and named output variables each receive their own port. Control edges express order, while data edges state exactly which property moves.

**The canvas draws each reference as a faint dotted line**: it only orders things (a node waits for whatever it references), **it never
makes the referenced node run**, it can't be selected, and hovering it says which reference it is. When the referenced node isn't wired
into the flow and will never run, the line turns the error colour.

![References drawn as faint dotted lines on the canvas (ordering only; they don’t make the referenced node run)](/media/screens/en/workflow-references.png)

<Recording src="/media/videos/en/workflow-editor.mp4" poster="/media/screens/en/workflow-references.png" caption="Live capture: reference tags, the start node’s parameter table, the readiness check and run history (a workflow of local-only nodes)" />

Each field can switch between **two input modes** (the small pill at the right of the label row):

- **Manual**: type a value / pick an option; in template fields press **`@`** to pull up upstream variables (keep typing to filter), or click a variable chip to insert at the cursor.
  Fields that point at something (3D scene, shot, timeline, track, project, account, connection…) are dropdowns: this workspace's items first, then upstream outputs;
  `{{loop.item.…}}` inside a loop body can be typed into the search box too. A dropdown that follows another field (shot follows scene, track follows timeline)
  says its choices are known at run time when that field comes from upstream. When the node has nothing upstream yet, `@` says so instead of doing nothing.
- **Connected**: the field becomes a port; pick one from the **upstream outputs** dropdown — equivalent to binding that reference. Switching back to manual keeps the previous value.

Code fields such as **Run script** and **Code** **don't interpolate references**: upstream values go into `input` and arrive as JSON data — text scraped from a page can't rewrite the script.

## Readiness check / run gating

The toolbar's **Readiness** button gathers every issue and shows a count: red blocks the run, amber is advisory, and with nothing left it
says all set — ready to run. It checks: a missing start node, missing required fields, one-of fields with nothing filled, stale references,
references to start parameters that don't exist, values outside their options, empty loop / subgraph bodies, an Output node inside a body,
nodes not wired into the flow, **references to nodes that will never run**, models / providers missing or without keys, type mismatches,
references written into code, plugin nodes that can't run (with the real reason)…

![The readiness list: “2 to resolve”, two required start parameters missing; click one to jump to its node](/media/screens/en/workflow-readiness-blocked.png)

- Problem nodes get a **warning badge** on the canvas with a tooltip listing the issues; each issue is clickable and jumps to the node.
- With blockers present the **Run** button is disabled, and ⌘Enter opens the readiness list instead.
- **A node that will run but references one that never will is stopped before the run**, naming who references whom and suggesting you
  wire it into the flow — or, for a graph built from an official template, use **Rebuild from the new version** at the top. Before, such a
  reference just came out empty.
- **There is one pre-run check**, shared by the editor's Run, sub-workflows, the agent's cards and scheduled tasks. A sub-workflow's
  required parameters, digital-human consent, a clone engine that isn't installed, an aspect ratio the video model won't take, or no chat
  model at all — each is reported before any node spends money.

Once a run starts, Run becomes **Stop run**, and ⌘Enter during a run doesn't start another one. The run's detail dialog in the task centre
carries **Cancel task** as well. Cancelling is **node-grained**: it stops after the current step finishes, whatever it already produced
(assets, timelines, 3D scenes) is kept, and derived sub-tasks are cancelled with it.

![Run history: every node of one real run and its time (asset query, tagging, text template, save as note — all local)](/media/screens/en/workflow-runs.png)

A few node details:

- **HTTP request** escapes upstream text inserted into a JSON body as JSON and sets `Content-Type`; **Fail on non-2xx** is on by default (switchable under Advanced).
- **Browser · run script** gives a script 20 seconds by default; long paged reads can raise the timeout under Advanced, up to 180 seconds.
- **Available 3D props** lists this workspace's 3D models as a catalogue (id, name, measured width/height/depth) to feed into the node that designs the blockout, so a set can hold real props.
- **Video to GIF** and **Split grid** always output **new assets** and never overwrite their input.
- LLM nodes use a **Preset** (Precise / Balanced / Creative) instead of a raw temperature, and a node's max output tokens never exceed the model's output limit.

## Analytics templates: accounts, viral videos, comments

The three analytics templates take a profile or post link (Douyin, Xiaohongshu, Bilibili), fetch the account, recent posts, video stats and top
comments, compute posting frequency and times, engagement, top posts and growth signals, and write it up as a note. Three nodes exist for them:
**Read a social media link**, **Tidy post and comment data** and **Download from a link**.

- **The data source is a two-way choice in the start node's `data_source` dropdown**: **Built-in browser** (no setup, no cost; Xiaohongshu always
  needs a sign-in and Douyin mostly does — switch the template's "Open in the built-in browser" step to the browser pool and pick a signed-in
  profile; Bilibili needs none; page numbers are rounded) or **TikHub** (install the TikHub plugin, create a connection and enable the tools the
  template lists on the Plugins page; billed per call, complete fields, no sign-in). If TikHub is chosen but not ready (plugin missing, no
  connection, tools not enabled, an extra connection for the same platform), **the run says what's missing before it starts** — or switch back
  to the browser.
- **Comment insights analyses every comment there is**: on Bilibili it pages through the site's own comment API (up to 1000, and says so if
  there are more, replies included); elsewhere it reads the comment section. All comments are taken 80 at a time, the model notes what it sees
  in each batch, and the notes are synthesised into the report — nothing is dropped however many there are. The comment-count parameter only
  sets how many top-liked comments go into the appendix table.
- A profile that isn't signed in to a platform that requires it reports "no comments fetched" rather than inventing any.

## Triggers

Use [Scheduled tasks](/docs/guides/scheduler) to attach a plan and inspect its run history.

Workflows can be bound to scheduled tasks: manual, cron, or webhook. Batch runs of the same workflow are supported.

<Aside type="caution" title="Scheduled tasks need the app running">

The scheduler runs inside the local backend, which is a child process of Mosael — **fully
quitting the app stops scheduled tasks from firing at all.**

That is why closing the window only tucks the app into the tray rather than quitting; use the tray
menu or ⌘Q to actually exit. To have it standing by from boot, turn on **Launch at login** under
Settings → Backend. Tasks missed while the app was closed run once on next start (the next
occurrence is recomputed from now, so missed runs do not pile up).

</Aside>

### Versions someone else changed

Version history shows who saved each version. When a run uses a private publishing account, browser
profile or files on this computer, both the person running it **and the author of the version being run**
(or someone who approved it) must be able to use them — a workflow started by a Call workflow node
counts with its own version too. If a teammate's version would borrow something of yours, the run stops
and names the workflow and version; after reviewing the change, click **Approve this version** in the run
history or version history. Approving doesn't change the graph or add a version.

## Let AI build it

The toolbar's **AI assistant** uses the shared persistent session pool: describe the flow you want
in natural language and it builds / edits nodes for you; changes go through confirmation cards. A card
that runs a workflow is titled with the workflow's name and pins the version it was opened on — if the graph
changes before you approve, it doesn't run and says which two versions differ.
Its top-left title is the active conversation — click it to search or switch sessions — and the
panel can dock beside the canvas or float above it.

## Comments and markers

The comment and flag buttons enter separate, mutually exclusive modes. Escape exits. Their eye buttons independently show or hide all comments or markers without deleting them. Markers are not listed in Add node.

In marker mode, click empty space to place a position bookmark, then set its name and jump shortcut. Only one marker editor opens per canvas. Clear a binding beside the shortcut field or remove the marker using the footer action. In comment mode, click empty space to write a comment and mention workspace members with `@`. Submitted mentions keep their interactive labels. Use the pencil to edit your own comment. Adjacent comment pins remain directly clickable.

Switching modes or undoing preserves graph connections. Toolbar groups use separators. Comments and markers are collaboration overlays and do not execute as graph nodes.
