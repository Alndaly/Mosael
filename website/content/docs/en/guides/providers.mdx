Mosael's AI features (agent chat, text-to-image / video, voiceover, transcription) are bring-your-own-key: most vendors take an **API key**, subscription plans use **authorized sign-in** (below). Credentials are stored by the connected backend and used to authenticate requests to the selected service. A remote backend stores them remotely. The settings API returns masked hints or authorization status.

## Configured per capability

Settings groups AI providers into four **capability sections**, each configured independently:

| Section | Used by |
| --- | --- |
| **AI Chat** | the agent and workflow LLM nodes |
| **AI Image** | text-to-image generation |
| **AI Video** | text-to-video generation |
| **AI Audio** | TTS voiceover / podcast synthesis |

At the top of each section is the **default model**: the default provider and model for that capability, overridable in place wherever it's used. The dropdown lists **models** (e.g. "DeepSeek · deepseek-v4-pro"), not providers — several models under one provider each appear on their own.

![Settings → AI chat: default model and provider configuration](/media/screens/en/settings-models.png)

**Configure providers per capability** — Chat / Image / Video / Audio each have their own section; after "Add provider" the UI renders exactly the fields that provider declares, and keys are stored locally:

![Demo: provider configuration entries for AI Chat and AI Image](/media/gifs/en/providers.gif)

## One connection is one endpoint plus one credential

A vendor is **not** a model or a connection. A connection records where the current user connects
and which credential they use, and it can hold **any number of models**. Endpoint/non-secret options
and API-key/OAuth state are stored separately so they can evolve independently, but both belong only
to their creator; Mosael never lists, selects, or falls back to another user's connection.
Click the chevron on a provider row to see that connection's model list.

## Add a provider

Click **Add provider** in the relevant section:

1. Pick a **vendor** (built-ins include Alibaba DashScope, Volcengine ARK (video / Seedream image), Evolink, Kimi, MiniMax, OpenAI, Google, Kuaishou Kling, OpenAI-compatible endpoints; the catalog grows over time).
2. Give it a **name** (e.g. "My Kimi").
3. Paste the **API key** (subscription plans have no key field — you authorize after saving instead). A "Get API key ↗" link jumps straight to that vendor's key console.
4. **Base URL**: API-key providers can leave it empty for the vendor default (shown as the
   placeholder); self-hosted OpenAI-compatible endpoints need it filled in. Subscription/OAuth
   providers neither expose nor need this field — their Provider Adapter owns the endpoint, so
   do not invent a service address for them.
5. **Model** is optional; if filled it becomes this provider's first model. You can add more at any time.

Providers can be **enabled / disabled** at any time without deleting.

### ByteDance: one company, two product protocols

Volcengine Ark's Seedream / Seedance generation APIs and Volcengine Speech's TTS / podcast APIs both
belong to ByteDance, but their consoles, credentials, endpoints and request protocols are not
interchangeable. Mosael groups them under one company namespace while retaining separate
Adapters and stable connection types; directory ownership does not merge the two credential sets.

### Evolink: several generation engines under one connection

Evolink is a unified image/video gateway. One Evolink API key can host Seedance, Kling, Veo,
Hailuo, WAN, Sora, GPT Image, Gemini and Seedream model rows under the same connection. Mosael
uploads local image, video and audio inputs through the Evolink Files API while preserving their
roles (keyframe, reference, edit source, or extension clip), submits the asynchronous task by exact
model id, then immediately downloads expiring results into the local media library.

This route is independent from the native Volcengine Seedance adapter, so you can choose it for
different regional, account or content-policy behaviour. Mosael adds no local "real person"
keyword block, but it cannot promise policy bypass: acceptance still belongs to Evolink's current
upstream model.

## Managing its models

Expand a provider row:

- **Add a model**: the "Add model…" field at the bottom is a **searchable** input listing catalog models you haven't configured yet. Catalogs run to hundreds of entries , so it searches rather than scrolls. Models absent from the catalog — private deployments, aliases — can simply be **typed in**; they work exactly like catalog ones and are only badged "not in catalog".
- **Enable / disable** a single model with the switch. Disabled models disappear from the default-model dropdown and every model picker.
- **Model settings** (gear icon):
  - **Capabilities**: which sections this model serves (chat / image / video / tts / podcast). Empty means "follow the vendor preset". This is how one endpoint expresses "a chat model *and* an image model".
  - **Context window**: decides how long a conversation can run before compaction kicks in. Defaults to the vendor catalog; when the catalog doesn't know the model, a conservative 32000 is used and you can override it. The line underneath says whether the current value is **yours, the catalog's, or the fallback**.
  - **Advanced** (collapsed): four compatibility switches — reasoning model, vision, reasoning effort, developer role. You only come here when an endpoint rejects a request; normally none of them need touching.
  - **Where parameters come from** (image/video models only; a model with both capabilities configures each separately): see the next section.
- **Delete** with the trash icon.

> The context window and the compatibility switches only show for **chat** models — asking an image model whether it supports the developer role is noise.

## Where an image/video model's parameters come from

The built-in table only holds models we have **verified**: which sizes they accept, what their duration cap is, whether they take a reference image. So this field defaults to **Detect automatically** — the model name is looked up in that table. When it is found, the matching knobs appear in the generation screen.

Three common reasons a model is not found: an alias you typed yourself (`gpt-image-2-client` is just gpt-image-2), a private deployment, or the same model configured through a relay endpoint. Two ways out:

- **"Same as ‹model›"** — point at a model we do recognise. It is a **pointer**: if we later widen that model's description, rows pointing at it follow. Prefer this.
- **"Describe this endpoint…"** (the link under the field) — when nothing in the catalog matches (a combination only your relay offers), write the parameter set yourself: tick the knobs this endpoint really accepts, say which values each one takes and where it starts, plus its hard limits and any quirks about request shape. Save and the row already points at it; renaming, editing and deleting are reached the same way.

Two things worth stating plainly:

- **We do not guess across vendors from the model name.** Measured on the same `qwen-image-edit`: Alibaba's own endpoint takes one reference image and no size; through Evolink it takes 14 and offers sizes. A guessed parameter is rejected by the endpoint on the spot.
- **When a model is unrecognised the screen does not pretend it simply has no parameters.** It names the fields that channel **can send** (the request is constructed by Mosael, so that part needs no verification) while saying nobody has verified which values this model accepts, which is why the generation screen does not offer them yet.
- Saving a parameter set only checks the **shape** (lists must be text, limits must be positive integers, a default must appear in its list). It cannot check "does this endpoint really support it" — only the endpoint knows that, and a wrong value fails when the provider rejects the generation request.

## Subscription plans: authorize instead of pasting a key

Claude Pro/Max, Kimi Code, ChatGPT Plus/Pro, GitHub Copilot, xAI and OpenRouter are **subscriptions** with no key to paste. Pick the matching entry when adding a provider under AI Chat, save, then click **Authorize** on that row:

1. Some vendors first ask for a **sign-in method** (Codex offers browser authorization or a device code).
2. The dialog shows an **authorization link** or a **device code**; complete it in your browser. Vendors that need a pasted code get an input field right there.
3. Once authorized, the models that account can actually use are pulled in automatically (Copilot's vary by plan tier; OpenRouter has hundreds).

**Tokens refresh themselves.** Expiry is simply how subscription tokens work — the app refreshes them when they're used and whenever you open Settings. Only a *failed* refresh (signed out elsewhere, authorization revoked) surfaces, in warning colour, as "re-authorization needed"; click **Re-authorize** then. **Revoke** disconnects the account.

When AI Studio analyzes an existing image or video with a subscription model, it keeps using the
**current session model**. The backend verifies the session from the agent's short-lived token and
sends images or sampled video frames through a tool-free, stateless Gateway. This is not a public
reverse proxy and it needs no `base_url`. Native whole-video input is not available through this
Gateway; choose Auto or Frames + transcript instead.

### Checking your quota

Subscription rows carry an extra **gauge icon** showing the current plan, each quota, and when it resets.

It is **fetched on click**. None of these quota endpoints is a documented public API (they're what each vendor's own CLI uses internally), so polling them on a timer would both trip rate limits and quietly rot into a permanently failing background task the day a vendor changes something. When a fetch fails, the message distinguishes "this vendor isn't supported" from "this attempt didn't succeed".

## Outbound proxy

When a vendor blocks your region (authorization or calls rejected, "region not supported"), set a proxy under Settings → **Network → Outbound proxy**. Both provider calls and authorization sign-in go through it.

- Loopback traffic **never** goes through the proxy (otherwise every agent tool call would break) — nothing to configure.
- The embedded browser is **unaffected**: publish-account logins carry their own per-account proxy.

## Retries on a flaky network

Settings → **Network** sets the retry count (on the same page as the outbound proxy: both answer "how do AI calls get out"). It applies to **every** AI call — chat, image, video, audio, embedding — because rate limits and 502s don't discriminate. On 429 / 5xx / connection failure the request retries with exponential backoff, with nothing required from you.

## Cost rules

Under Settings → **Cost rules** you can price models (per token / per image / per second); Statistics and the task center accumulate AI spend accordingly. Unpriced usage is labeled "unpriced". On the Statistics page, the "N unpriced" count in the AI usage tile links straight here.

**Prefill prices** creates rules in bulk from two sources — per provider, or for all of them with **Prefill all**:

- **The provider's own model catalog**, when it carries prices (OpenRouter, or the catalog a subscription sign-in brings back), takes precedence.
- When the catalog has no prices (true of most OpenAI-compatible endpoints), the app's built-in **official price list** fills the gap: DeepSeek, Kimi, Alibaba Bailian (chat, Wan video, image, speech), Volcengine Ark (Seedance video, Seedream image), Volcengine speech, MiniMax (chat, Hailuo video), OpenAI (chat, GPT Image, TTS), Anthropic, xAI and Google Veo. Every entry was checked on the vendor's official pricing page; each rule's note cites the page and the check date. Currency follows the vendor's list (CNY for Chinese vendors, USD otherwise), and an international endpoint gets the international price. Tiered pricing (peak/off-peak, context length) records one tier and names the others in the note.
- Relays (custom OpenAI-compatible addresses, Evolink and the like) borrow a vendor's list price only when the model id belongs to exactly one vendor, and the note warns that the relay may charge differently.

Two rules stay the same: it only fills what's **missing** and never touches what you've already entered (your prices may include a discount or an enterprise agreement), and a price of 0 produces no rule — that means "unpriced / included in the subscription", not "free". After prefilling, each provider gets its own result line: how many rules came from the catalog and from the price list, and which models still need a price by hand.

## Bindings: missing config surfaces where it's needed

Models are **bound** to the places that use them. When something isn't configured, that place tells you and links to the fix:

- Workflow **LLM / AI-generate nodes**: with no usable provider (or a deleted one referenced), the inspector shows an amber / red banner with a "Configure" shortcut.
- **AI Studio** generation: with no usable generation model, the list shows the same prompt.

> The generation model catalog always has built-in entries; whether they actually run depends on **the corresponding vendor key being configured**.
