## 0. 一句话

> **这套代码用「同一份语义要在多处成立」换来了它的清晰度,用棘轮来保证那个"多处"不失守。
> 本次五路审计的 55 条问题里,压倒性多数不是纪律没执行,而是执行纪律的那台机器自己有一个
> 没人看的角落 —— 盲区递归了一层。**

规模上的判断要先说清楚,否则下面的清单会给错印象:102 条棘轮与文档自动同步、11 份契约语料
两侧都真的在跑、CI 是主干与发版共用的同一份、迁移有显式 phase 与记账、数据归属有声明式地图、
领域异常而非 HTTPException 四处同构。**这些都不是文档里的愿望,五份报告各自独立查证过。**
下面挑出来的,几乎全是「机制已经建好,边界画在了错的地方」,不是「没建」。

## 1. 三个盲区,和它们其实是同一个

五份报告是**分头写的**,互相看不见。它们各自命名的失败模式,合起来只有三种 —— 而这三种
是同一个根因在三个高度上的样子。

### 盲区一:链条的最后一环(已知,本次确认为普遍)

链条审计已经提过:**一个值在链条的 N−1 环都在,最后一环没接上,两边都不报错。** 本次五份
里全部独立复现:

| 报告 | 实例 |
| --- | --- |
| 前端 | `linked_clip_id` 四层都有(建表、接口 schema、撤销恢复、生成的 TS 类型),**没有任何一处写它**;`WorkspaceSummaryOut` 八个用量字段后端算完没人读 |
| 后端领域 | 子工作流输出契约的 `or` 回退;节点 `label` 当人话落库;任务消息的 i18n |
| AI 供应商 | 降级三处触发点、零处记录;放行判断每次真花钱而账上一条没有 |
| 进程边界 | sidecar 说了「这条没接住」而后端从不读那句话 |

**复核**:`linked_clip_id` 全仓 6 处引用,唯一的写入是 `undo/rows.py:48` 从一份**没有任何
代码生产**的 payload 里恢复它 —— 四层俱全的一条死管线。属实。

### 盲区二:棘轮的判据是对的,扫描面停在写它那天(新,最要紧)

工程体系那份抽查了 12 条棘轮并逐条尝试绕过:**5 条 ❌ 能被绕过,2 条 ⚠️ 只覆盖一半,5 条 ✅ 真能拦住。**
关键在于失手的方式高度一致 —— **规则写对了,扫的范围没跟上**:

| 棘轮 | 它要防的事 | 它实际扫的 |
| --- | --- | --- |
| `test_executor_outputs_are_declared` | 执行器返回的键都声明过 | 只认 `ast.Assign`,不认 `ast.AnnAssign`;**读不懂就 `continue`** |
| `test_nobody_writes_prose_into_job_message` | 别把中文写进任务消息 | 只扫 `job.message = "中文"`,扫不到 `say(job, "中文")` |
| `test_data_ownership_ratchet` | 行只在拥有方建 | **整个 `app/api/routes/` 豁免** |
| `unlayeredGlobals.test.ts` | 不分层的 CSS 会压死整族工具类 | 只读 `tokens.css` 一个文件 |
| `lib/typeScale.test.ts` | 不许写死字号 | 只扫 `.ts`/`.tsx`,且只认 `text-[Npx]` |
| `test_database_upgrade_safety` | 升级前先拍快照 | **自己先把 `user_version` 改成 0 才验**,所以永远绿 |
| `featureBoundaries.test.ts` | 功能模块不许成环 | 只拦二元环 |

**复核**:数据归属那条我自己数过 —— 被豁免的 `app/api/routes/` 下有 **19 处直接建行**,
其中约 10 处所建的表,声明的拥有方只有领域模块(`Asset` → `app/domain/assets/`、
`Sequence`/`Track` → `app/domain/sequences/`、`TtsConfig`、`FeishuBot`、`projects.py` 里的
`Workspace`/`WorkspaceMember`)。**声明在那儿,而声明说的话在那一层不算数。**

这一条比盲区一严重一个量级,理由是:**一条在它该响的那次保持沉默的棘轮,比没有更坏** ——
它还让人放心。`test_database_upgrade_safety` 是最干净的例子:测试绿了 17 个版本,而它守的那道
保险从 2026-09-04 起实际是关着的,期间新增 14 条迁移,含两处 `DROP TABLE` 加一次搬文件目录。

### 盲区三:同一件事的第 N 条路(新,出现在全部五份里)

这一条我在链条审计里已经给过一个说法,本次五份把它坐实成了**最普遍**的那个形状:

> **同一件事有 N 条路,其中 N−1 条学到了教训,剩下那条没有 —— 而那条教训往往就写在隔壁文件里。**

| 学到了的那条 | 没学到的那条 | 出处 |
| --- | --- | --- |
| 发布执行器的多执行器围栏(一整页注释 + `test_two_publish_workers.py`) | 并排的浏览器执行器,一条都没有 | 进程边界 2.3 |
| Python 常驻 worker 的 `getppid()` 看门狗 + 专门测试 | 花钱又写库的 pi sidecar,没有 | 进程边界 |
| `Job.message` 学会了"别冻结中文,存 key" | 确认卡的措辞正好相反:写入时冻结中文 | 后端领域 2.5 |
| 模型目录的鉴权规矩修过一处 | 本地 / 无鉴权端点那条路没修 | AI 供应商 2.5 |
| 一个聊天面板的流式协议 | 另一个面板各实现一遍,**已经分岔** | 前端 2.3 |
| 后端把凭据租约分成两种 409 | sidecar 把两种当成同一种 → 下一轮被登出 | 进程边界 2.2 |

### 为什么这三个是同一个

把它们叠起来看:

- 盲区一是**业务代码**里"还有一处没改到";
- 盲区三是**同级的另一条路**没改到;
- 盲区二是**棘轮**自己的"还有一处没扫到"。

三者的共同结构是:**正确性依赖"某处也要成立",而"有哪些处"这件事本身没有被写下来,
靠人记得。** 棘轮的发明正是为了把"记得"自动化 —— 但棘轮也是代码,它也有一个"有哪些处",
也靠人记得。**于是盲区没有被消灭,只是上移了一层,而上面那层没人再看。**

这解释了为什么本次最严重的两条(快照关着、归属豁免)都出在棘轮层,而不是业务层:
业务层有棘轮盯着,棘轮层没有。

## 3. 本次就地修掉的

综合不是只写字。这五份报告指出的问题里,已经动手的两条是**盲区二**的两条,因为它们是
"守门那层自己失守",不修的话后面每一条修复都少一道验证:

| 提交 | 内容 |
| --- | --- |
| `d2d7e16a` | 升级快照的触发判据从「一个要人记得改的版本号」换成 `MigrationPlan.pending()` —— 待跑的一次性迁移有几条,这个数从迁移本身算出来,加迁移时不需要谁记得再改一处别的 |
| `770be6c3` | 执行器输出棘轮**每一个**执行器都真的读出了形状:读不懂改成断言而不是 `continue`;顺带认了 `{**spread}`(顺着赋值追到 `read_reference`)和带类型标注的赋值 |

第二条值得展开一句,因为它是**盲区二的通用解法**:那条棘轮点名的两个执行器,查下去发现
**两个都是读的那一侧短,不是被查的代码有问题**。`browser_close` 的 `return {}` 被误报,是因为
"没有键"和"读不出来"都返回了空集合。**棘轮误报和漏报一样坏** —— 它教人学会忽略它。
判据因此是两条而不是一条:看不懂要说出来(不能静默跳过),看得懂的不能乱说(不能误报)。

另修:三处智能体报告里指向不存在文件的路径 —— 由 `test_docs_do_not_point_at_ghosts` 当场
拦下,是本次**唯一一条在真实新增内容上当场生效**的棘轮。

## 4. 建议的下一步(排序的,每条带判据)

1. **修进程边界 2.4(`finish()` 的顺序)。** 最便宜的高危。判据:停止一轮之后,会话状态在
   看门狗超时内回到可用,而不是永久「思考中」。
2. **把盲区二做成可检查的,而不是再抽查一次。** 棘轮要能说出**自己扫了什么、跳过了什么**。
   `770be6c3` 的改法就是样板:凡是静态读不出来的,断言报出来并要求登记理由,登记表只减不增。
   判据:随便挑一条棘轮,能回答"它扫不到哪类写法"这个问题,而不需要读它的源码。
3. **给"第 N 条路"建一份清单。** 盲区三的每一条,都是因为"有哪些条路"没写在任何地方。
   仓库里已经有现成的样板 —— `domain/ownership.py` 就是把"谁能建这张表"写成了数据。
   同样该写成数据的至少有三处:**执行 AI 请求的通道**(直连 HTTP / pi sidecar)、
   **长活子进程**(发布 worker / 浏览器执行器 / Python worker / pi sidecar)、
   **流式聊天面板**。判据:加第四条通道时,有一处会红。
4. **补三类跨进程契约语料。** 现有 11 份语料钉的全是**数据形状**;进程边界那份最贵的三条
   钉的是**回执、时限、身份** —— 这三类今天一份语料都没有,而它们恰好是两个运行时之间
   最容易各自理解的东西。
5. **归属豁免收窄。** 不是取消 `app/api/routes/` 豁免(路由确实是薄转译),而是把它从
   "整层豁免"改成"逐表声明":路由要建某张表的行,就在 `TABLE_OWNERS` 里把那条路由写进去。
   ~19 处里约 9 处本来就已经声明了路由为拥有方,真正要处理的是剩下的约 10 处。

## 5. 一处需要往回修的结论

**AI 供应商那份 §0 说「`model_limits`、`thinking`、`structured_output` 三张表只接到了
sidecar 一侧」—— 三张里有一张说错了。** 我复核的结果:

- `model_limits` —— **属实**。全仓只有 `provider_runtime.py`(sidecar 那条)和 `agent/host.py`
  读它;`ai_chat.py` 连 import 都没有,那八个直连调用点拿不到任何上限。
- `thinking` —— **半属实**。直连那条上它不是"读不到表",而是 `ai_chat.py:171-179` 一段**写死的
  启发式**(DeepSeek V4 默认关思考,把预算留给可解析结果),旁边写着理由。问题是它和表里
  查证过的事实没有对齐关系,不是它不存在。
- `structured_output` —— **不属实**。`ai_chat.py:130-139` 的 `_structured_output()` 明确读了
  `structured_output.effective_support(...)`,直连这条路上是接着的。

结论的方向不变(**两条通道从来没有被要求对齐过**,这一点三张表都成立),但"一张都没接"
要改成"一张接了、一张写死、一张没接"。

把这一条单独列出来,是因为它正是这次综合该干的活:**五份报告分头写,谁也验不了谁。
综合如果只是把它们加起来,就是把五份的置信度乘在一起当成一份的。**

## 6. 对 2026-09-21 链条审计的一处更正

那一份 §4「没有发现问题的地方」把**数据归属**列为"棘轮在按设计工作,没有出现第二处建行"。
这句话在我当时查的那张表(`Scene3DModel`)上成立,但**作为一条关于机制的结论是错的** ——
`ownership.py:117` 豁免了整个 `app/api/routes/`,而那下面有 19 处直接建行。

我当时查的是"我改的那张表对不对",写下的却是"这个机制没问题"。**从一个样本推广到机制,
正是本文 §1 那三个盲区的同一个动作。** 已在该文中就地更正。
