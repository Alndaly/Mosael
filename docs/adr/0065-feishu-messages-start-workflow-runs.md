# ADR 0065:飞书消息触发工作流 —— 触发器是一等数据,命中即认领这条消息

## Status

Accepted — 2026-10-16,已实现(见文末「实现记录」)。一笔从零建的子系统:`workflow_triggers` /
`workflow_trigger_events` 两张表、`domain/triggers/`、`/api/workflow-triggers`、工作流卡片菜单里的
「触发器」面板,以及入站那一处的匹配接线。

**一句话的目标**:群里丢一条视频 → 自动跑一条工作流。以前只能靠智能体会话(它看不懂视频),
或者靠定时任务 / webhook(它们不知道"群里刚来了一条视频")。

## Context

### 飞书入站只有一条路:喂给智能体

`integrations/feishu/inbound.handle_incoming` 是消息唯一的入口。它做的事:去重(`seen_recently`,
进程内、300 秒)→ 认机器人 → 认人(`bindings.resolve_sender`,没绑定就回一句绑定指引)→
图片进素材库 → `host.post_user_message` 交给**和桌面端同一条** turn 管线 → 回复由
`deliver_turn` 送回原会话。

`text` / `post` / `image` 之外的类型**根本没有下游**:`SUPPORTED_MESSAGE_TYPES` 之外的消息
(`file` / `media` / `audio` / `sticker` …)当场回一句「我暂时看不了视频」就结束了。也就是说
维护者要的那条路(丢视频 → 跑工作流),在那条链路上**没有任何位置可放**。

### 仓库里已经有的两种"自动跑一次工作流"

| 机制 | 它是什么 | 为什么这里不直接复用 |
| --- | --- | --- |
| 定时任务(`scheduled_tasks`,`trigger_type=schedule/once/webhook`) | 到点或凭 webhook 密钥起一次运行;`SCHEDULED_EXECUTORS["workflow"]` 复用包装任务,`start_workflow_job` 在上面推进度 | 它的判据是**时间**或**一把密钥**,不是"群里来了一条什么消息"。它没有消息类型 / 关键词 / 发件人这些筛选,也没有"这条消息对应哪次运行"的留痕 |
| 智能体会话 | 每条消息都以绑定成员的身份跑一轮 turn,回复发回群 | 它看不懂文件 / 视频(`SUPPORTED_MESSAGE_TYPES`),而且每一轮都要花一次模型钱 |

"一条消息该不该起一次运行"是一个**新问题**:要有筛选(类型 / 关键词 / 谁发的)、要有去重与限流、
要在两条既有链路之间**明确谁优先**。这三样都不属于定时任务,也不属于智能体会话。

### 运行入口只有一个,必须复用

`domain/workflows/engine.start_workflow_job` 是"开始一次运行"的唯一用例:它钉住当前修订、
跑 `check_runnable`(结构 / 必填 / 插件按跑的人 / 运行前检查 / 子流程)、按跑的人判 ADR 0047 的
担保、建(或复用)任务、经 `dispatch_job` 派发。**触发器不另拼一套** —— 它和点「运行」、智能体的
「运行工作流」卡、定时任务走的是同一个函数。差别只在两格:`created_by`(替谁跑)与 `params`(入参)。

## Decision

### 1. 触发器是一条一等数据,不是工作流图的一部分

新表 `workflow_triggers`(见 `db/model_slices/triggers.py`):

| 列 | 意思 |
| --- | --- |
| `workspace_id` / `workflow_id` | 哪条工作流。删工作流时**当场停用**(不删行,留痕)。`workflow_id` **不设外键** —— 设了就会跟着级联删掉,"这里原本挂着一条自动化、它跑过几次"的痕迹也跟着没了(和定时任务把 `workflow_id` 放在 payload 里同一个取舍) |
| `owner_user_id` | 谁的触发器。**跑的时候替这个人跑**(钥匙、额度、ADR 0047 的担保都是他的),和 `ScheduledTask.owner_user_id` 同一条规矩 |
| `name` | 给人看的名字(回执里点名它是谁) |
| `bot_id` | 哪个机器人。空串 = 这个工作区里**任意**机器人(见 `domain/feishu/bots`) |
| `chat_id` | 哪个群。空串 = 这个机器人所在的**任意**群 |
| `message_types` | 认哪些消息类型:`text`(含富文本 post)/ `image` / `file` / `media`(视频)。空表 = 不认任何类型 |
| `keywords` | 可选。非空时,消息文本里要**出现任意一个**(大小写不敏感)才算命中 |
| `only_from_open_ids` | 可选。非空时,只认这些飞书 open_id 发的消息 |
| `params` | 入参映射,见下 |
| `reply_in_chat` | 要不要在群里说话(起跑回执 + 跑完的结果)。默认开 |
| `max_runs_per_minute` | 限流,见 §4。默认 6 |
| `enabled` | 开关。**关掉就是关掉**:`claimable` 这一步只查启用中的,停用的连匹配都不进 |
| `last_fired_at` | 留痕:上一次真的起跑了是什么时候 |

**为什么不做成定时任务的一种 `trigger_type`**:定时任务的判据是时间/密钥,它的 `payload` 是
一张固定的入参字典;而触发器要按**这一次的消息**算筛选和入参,还要留"这条消息 → 这次运行"的痕。
把它塞进 `scheduled_tasks` 会让那张表的两个语义打架(`schedule` 与 `message_types` 互不相干),
而且启用/停用、就绪检查、运行记录全都要按 `trigger_type` 分叉。**新表更小**:一张配置、一张事件。

**为什么不做成工作流图里的一个节点**:图是在编辑器里被改的、每存一次就是一版修订;而触发器是
"这张图被谁在什么群里怎么叫起来"的**外部配置**,它不该参与图哈希、不该出现在画布上、也不该
因为同事改了一次图就连带失效。放在图里还会让 `revisions` 的不可变语义多一层解释。

### 2. 入参映射:字面模板,`{{trigger.*}}` 是唯一的作用域名

`params` 是 `{"<开始节点参数名>": "<模板>"}`,模板里可以写这些占位符(白名单,`matching.TRIGGER_FIELDS`):

| 占位符 | 值 |
| --- | --- |
| `{{trigger.text}}` | 消息文本(提到自己的 @ 已剥掉;富文本的标题与正文都算) |
| `{{trigger.message_id}}` | 这条消息的 id |
| `{{trigger.chat_id}}` / `{{trigger.bot_id}}` | 从哪来 |
| `{{trigger.sender_open_id}}` | 谁发的 |
| `{{trigger.message_type}}` | `text` / `post` / `image` / `file` / `media` |
| `{{trigger.file_name}}` | 文件名(文件 / 视频消息才有) |
| `{{trigger.asset_id}}` | **第一份**入素材库的素材 id(图片 / 文件 / 视频) |
| `{{trigger.asset_ids}}` | 全部素材 id,逗号分隔 |

- **保存时就校验**:模板里出现白名单之外的 `{{trigger.x}}` → 422。配置错误不该等到群里
  真发了东西才暴露。
- **只在触发器这一层解析**。`{{trigger.*}}` **不是**引擎的作用域名 —— 不去动 `binding.interpolate`
  那条路(它解析的是节点输出,加一个新根会让"引用指不到"那套判据多一整个域),引擎也因此
  完全不知道触发器的存在。解析出来的值以 `params` 的形式交给 `start_workflow_job`,之后它就是
  一次普通运行:开始节点的参数。
- **同名直填**(方便上手):`params` 里没提到的开始节点参数,只要名字**正好**是上面那几样
  (`text` / `asset_id` / `file_name` / `message_id` / `chat_id`),就用对应的值填上。一个开始节点
  里有一个叫 `text` 的参数,不必再配一行映射。这一条是**便利**,不是协议:显式映射永远更优先。

### 3. 与智能体会话的关系:**命中即认领,这一条不再喂智能体**(不是两条都跑)

**拍板:一条消息只要被**任意一条启用中的触发器认领**,就不再交给智能体会话。两条不都跑。**

理由:

1. **两条都跑 = 双倍花费,而且是双份回答**。丢一个视频进群,智能体会话那一轮会回一句
   「我暂时看不了视频」(它本来就只认文字/图片),同一刻触发器又起了一次运行 —— 群里看到的是
   一句莫名其妙的拒绝加一条运行,用户第一反应是"它到底有没有收到"。
2. **同一个事实有两个主人**。消息该不该触发,是一道**筛选**;筛选的结论如果是"这条归我",
   再让另一条链路也去解释同一条消息,两边的结论迟早不一致(触发器限流了、智能体照样回一段话)。
3. **可解释**。用户要能一眼看出"这次是触发器起的"。认领制让这件事只有一个答案(见下),
   而不是"这次既是触发器又是对话,看哪条先跑完"。

**用户怎么看得出这次是触发器起的**:三处,都在一条消息的生命周期里——

1. **群里一条回执**:`已按触发器「视频入库」开始运行「视频转码」`(`reply_in_chat=true` 时,
   `triggerReceipt` 文案)。这句和智能体会话的回复完全不同,而且**点了触发器的名字**;
2. **触发器面板里的「最近触发」**:每一行是"哪条消息 → 哪次运行",带状态与失败原因;
3. **那次运行的任务卡**:`job.payload` 里有 `trigger_id` / `trigger_event_id`,运行历史里看得到。

关掉 `reply_in_chat` 之后群里不再回执,但 2、3 两处照样在 —— 留痕不依赖群消息。

**没被认领的消息照旧走智能体**:筛选不命中(类型不对、关键词不对、发件人不对、限流了)时
一切如常,会话链路一个字节都没变。

**为什么不是"触发器优先、但智能体也知道这件事"**:那样还是要多跑一轮 turn,只是内容不同 ——
双倍花费那一半没解决,换来的是"智能体也看得到这条消息"这一点点信息。真要它知道,工作流跑完的
结果可以落进会话,那是以后的事(见 §6)。

### 4. 匹配、去重、限流

**匹配**(纯函数,`matching.decide`,不认识数据库、单测覆盖):

```
机器人对得上(bot_id 为空 = 任意)  且
群对得上(chat_id 为空 = 任意)     且
消息类型在 message_types 里        且   ← text 与 post 归一成 text
发件人在 only_from_open_ids 里(空 = 不限) 且
keywords 为空,或文本里出现任意一个(大小写不敏感)
```

**只有绑定了 Mosael 账号、且在该工作区有 `edit` 的人能驱动触发器**。这一条不在 `matching` 里,
而是入站链路上**先于**触发器的既有规矩:没绑定的人连 `SUPPORTED_MESSAGE_TYPES` 那条路都进不去
(得到的是绑定指引)。触发器沿用同一条:未绑定的消息在认人那一步就被拦下,**根本轮不到匹配**;
只读成员也不会命中触发器(否则等于用触发器主人的钥匙和额度跑自动化,却把结果发回他所在的群)。
理由:机器人是以工作区成员的身份行事的,触发器还要花那个人的钥匙与额度 —— "群里谁都能触发"
会把额度交给整个群。

**去重**:`(trigger_id, message_id)` 上的**唯一约束**(`workflow_trigger_events`)。

- 飞书会重复投递同一条消息(长连接重连、事件重放)。进程内那条 `seen_recently` 只活 300 秒、
  重启就没了 —— 而"重启之后飞书又推了一遍"**正是**会造成第二次付费运行的那一刻。
- 所以判据落在**库里**:处理一条消息时**先写一行事件**(先读一次,读到就当场跳过;写下去的是
  唯一约束,撞上就是重复),拿到这一行才继续起运行。一行事件对应一条触发器 × 一条消息。
- 不撞约束是**快路径**:先读一次,免得一个常见的重复投递把整个事务打进"需要回滚"的状态
  (那个事务里还有附件入库的记录、别的触发器的认领)。真并发撞上唯一约束的后果是**这一次
  整个回滚**:宁可少跑一次,绝不付费跑两次。
- 同一条消息被两条触发器认领 → 两行、两次运行(这是配置本意,不是重复)。

**限流**:**每个触发器每分钟最多 `max_runs_per_minute` 次真正起跑**(默认 6,上限 60)。

- 判据也是库里的:**最近 60 秒内状态为 `started` 的事件行数** ≥ 上限就限流。
- 数在库里而不是内存里:重启不清零(和去重同一条理由 —— 风暴之后紧跟着一次重启,进程内的
  计数器会从 0 重新开始)。
- 被限流的消息**照样留一行事件**(`status=throttled`),所以"触发器看着挺闲其实一直在被丢"
  这件事在面板上看得见。
- **一条消息最多认领 3 条触发器**(`MAX_CLAIMS_PER_MESSAGE`):一个工作区里十条都能匹配同一句话时,
  一句话不该起十次运行。按创建时间先到先得,落选的那些记一行 `status=skipped`。
  这一条是**兜底**,不是常用路径 —— 正常配置下一条消息只该被一条触发器认领。
- **不做队列/合并**:限流之内的并发运行照常起(一条消息一个运行,前后消息互相不等)。工作流
  本身是 IO 型、任务总线有派发名额,合并会引入"这条消息等上一条"的新语义,不值。

### 5. 失败与不可用:留痕优先,群里不喊配置错误

| 情形 | 做什么 |
| --- | --- |
| 机器人没了 / 停用 | 消息本来就到不了这里(`handle_incoming` 第一道就 `return`),**什么都不做** —— 没有 bot 就没有入站 |
| 工作流被删 | 删工作流的那一刻,绑着它的触发器**当场停用**(和定时任务 `stop_tasks_bound_to_workflow` 同一条规矩,同一个事务)。竞态下仍然命中:记一行 `refused`,**站内通知**给触发器的主人,不自动重试 |
| 图跑不起来(缺必填、插件连接落不了、ADR 0047 那一版要认可) | 记一行 `refused`,带 `check_runnable` 的原话;站内通知 |
| 起运行的时候抛了别的异常 | 记一行 `failed`,带异常原文;站内通知 |
| 被限流 | 记一行 `throttled`。**不通知**(通知本身就是另一种风暴) |

**为什么拒绝时群里不回话**:群里的人改不了这条配置,回一句"工作流配置有问题"只是把配置错误
喊给一整群人,而且在风暴里会跟着每一条消息重复。要喊的人在**站内**喊得到:通知 + 触发器面板上
那一行红的 + `last_fired_at`。这一条与"智能体会话出错会回一句"故意不同 —— 会话那一边,**发消息
的人自己**是能重试的那一方(换个说法、重发一次),触发器这一边不是。

**起跑成功时群里回一句**(`reply_in_chat`),失败**不**回。于是群里的信号很简单:**有回执 = 跑起来了**。

### 6. 这一笔不做的

- **非飞书来源的触发器**(定时 / webhook / HTTP):**不实现**。扩展方式已经摆好了——
  `domain/triggers/dispatch.handle_message` 收的是一个 `Message`(workspace / bot / chat /
  消息 id / 发件人 / 类型 / 文本 / 素材 id),不认飞书;`WorkflowTrigger.bot_id` / `chat_id`
  为空串就是"任意来源",加一种来源 = 写一个适配器把它的消息包成 `Message`,再在它自己的入口
  调一次(定时与 webhook 那一边已经有 `ScheduledTask`,`trigger_type` 就是现成的挂点)。
- **产出里的图片 / 音频传回飞书**:`integrations/feishu/client.py` 没有"上传图片拿 img_key"
  的口子(`send_card` 只能发文字卡),结果回群里目前是**文本 + 状态**。要传图得先给 client
  加一个上传函数(那一层属于另一笔在途的改动,不在这次的范围里)。
- **把运行结果落进智能体会话**:触发器认领之后那次运行与 `AgentSession` 没有任何关系。
- **回群里做富文本卡片**:目前是纯文本回执(`client.send_text`),卡片留给以后。
- **对"人"的粒度做去重**:同一个人连发五条不同的消息就是五次运行(在限流之内)。按人合并
  需要引入"等一会儿再跑"的窗口,会和"群里丢一条就跑"直接冲突。

## Consequences

- 入站链路多了一个**先于类型检查**的分支:能触发器的消息类型是 `text/post/image/file/media`,
  其中 `file` / `media` 在**没有**触发器接的时候,行为和以前一模一样(回一句「看不了」)。
  唯一的差别:这两类消息现在会先认人 —— **未绑定**的人发文件/视频,得到的是绑定指引而不是
  「看不了」(以前是后者)。这是一处**有意的**改进:先绑定,比先告诉一个陌生人"我看不了视频"有用。
- `workflows/readiness` 那套检查现在被第四个入口调用(点运行 / 智能体卡 / 定时任务 / 触发器)。
  引擎不动,调用方各问一次。
- 触发器面板要能回答"它在干活吗",所以 `workflow_trigger_events` 是有意**不清理**的(和
  `scheduled_task_runs` 一样,行随触发器删)。要清理的话按 `created_at` 定一条保留期,不是这次的事。

   素材库……换一个或稍后再试"),而这一次**不起运行** —— 素材就是入参,缺了起一次注定失败的运行没有意义。
   日志里分得清是"下载取不回来"还是"素材库不收这种文件",对人都是"换一个"。
2. **起跑失败不在群里喊**(§5 那条照旧):`create_job` 之后再抛的异常记一行 `failed` + 异常原文、
   `job.payload` 留着 `trigger_id` / `trigger_event_id`(运行历史据此说得出"这次是触发器起的"),
   站内通知主人。
3. **失败通知每分钟最多一条**:`_notified_recently` 按 `(trigger_id, 最近 60 秒内有没有坏状态事件)`
   判,而且**在写下这一次的坏事件之前**判 —— 否则 `_notified_recently` 看到的是它自己。
4. **去重前置**:`dispatch.unrecorded_claims` 在**附件下载之前**问一次"这条消息已经为这些触发器留过痕没有"。
   判据还是 `(trigger_id, message_id)` 上的唯一约束,但**附件入库自己 commit** —— 等到 `fire` 里那一道
   去重才拦,运行是挡住了,素材已经白多一份。
5. **被限流的消息回落到智能体会话**:这正是 §3「没被认领的消息照旧走智能体……(限流了)」那句话
   (`inbound._left_for_the_agent`)。判据是"**认领过**的那些结论非空、且全是 `throttled`" ——
   落选的 `skipped` 不算(它和这条消息有没有起过运行无关),**一条结论都没有**也不算(那是重投或
   触发器在两步之间被关掉,不能当成"没人要",否则同一条消息会再喂一轮)。
6. **回执发送包 try**:一条发不出去不能带走后面几条 —— 能走到那里的运行**都已经起了**,抛出去就是
   `feishu-inbound` 那条线程带着未处理异常结束。捕得比 `deliver_turn` 宽:飞书自己的错是 `FeishuError`,
   而网络抖动是 `httpx.RequestError`。
7. **图已删的触发器不能再被打开**:`triggers.use_cases.update` 在 `enabled=True` 之前顺手看一眼那张图
   还在不在(和 `create` 已有的那一道同一条)。此前那一格会返回 200,让一条注定跑不起来的自动化
   在面板上显示成"开着",直到下一条消息才 `refused` + 自停。
8. **三处机械 bug**(`ad6775dcb`,同一族代码):`limit=0` / 非法 `channel` / `raw` 前缀写法
   (见 [ADR 0066](0066-feishu-is-a-first-class-citizen-of-the-workflow.md) 的补记)。
