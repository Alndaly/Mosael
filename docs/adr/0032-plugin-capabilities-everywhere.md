# ADR 0032 · 宿主能力是一张表,插件在每一项上都能注册实现

- 状态:已采纳(2026-09-28,维护者要求「很多地方都应该支持插件动态注册能力,整体过一遍并放开权限」)
- 相关:ADR 0020(插件做生成供应商)、ADR 0031 §5(宿主能力是一张表 —— 本 ADR 把它推到所有引擎)

## 背景:盘点现状

插件清单里的 `provides` 是一个开放词表,但宿主只认得其中三项,而且认的方式各不相同:

| 能力 | 宿主那边怎么挑实现 | 插件能不能插进来 | 在哪里能点名用 |
| --- | --- | --- | --- |
| `generation` | 连接 + 模型行(ADR 0020) | 能 | 所有生成入口的模型下拉 |
| `public_url` | 能力表 `domain/capabilities` | 能 | 只在生成漏斗里自动用 |
| `document_parse` | 能力表 | 能 | 文档详情「重新解析」、设置默认;(本 ADR 之前一天才加上工作流和智能体) |
| 降噪 | `ai/providers/registry.DENOISE_ADAPTERS`,进程全局 | **不能** | 节点里写死 `auto / ffmpeg / deepfilternet / rnnoise` |
| 分离人声 | `SEPARATION_ADAPTERS`,进程全局 | **不能** | 写死 `auto / demucs` |
| 转写 | `ai/runtime` 的 ASR worker | **不能** | 写死 `auto / funasr / whisperx` |
| 翻译 | `domain/translate` 里 `if engine == "ai"` | **不能** | 写死 `google / ai` |
| 配音 | `voices/engine_catalog` 手写五家 | **不能** | `speech_engines`(现查,但只查手写的那五家) |

另外还有第二张表 `plugins/host_capabilities`(实例变动时通知宿主侧、插件页列出「它提供了哪些模型」),和
能力表是两套登记。

用户看到的后果:

- 想提供一个降噪 / 转写 / 翻译 / 配音引擎的插件,**没有地方插**;
- 只经宿主调用的工具(`HOST_ONLY_CAPABILITIES`)在插件页上是一片空白,没法「试一下」;
- 「用在哪」是手写的一句文案(用户截图:「为何这个能力的列表不是动态的」),新入口用上它不会自己出现。

## 决定

### 1. 一张能力表,每项能力一份契约

`domain/capabilities` 是唯一的表。每项宿主能力登记一份 `Capability`,说清楚:

- **名字**:清单 `provides` 里写的那个词;标签、说明;
- **内置提供方**:零个到多个。本地引擎就是内置提供方(降噪的 ffmpeg / rnnoise / deepfilternet、分离的 demucs、
  转写的 funasr / whisperx、翻译的 google / 对话模型、配音的五家);每个内置提供方报自己「此刻跑不跑得起来」
  (没装依赖、缺 Key 的列出来但标缺什么,和插件连接缺配置是同一种「missing」);
- **插件协议**:宿主怎么调认领这项能力的插件工具(准备什么输入、收什么产出、进度与取消)。协议把插件工具包成
  这一族的适配器 —— 调用方拿到的永远是这一族的适配器,不关心它背后是本地引擎还是哪个插件;
- **挑法**:沿用 0031 那一份(他定的默认 > 内置 > 只有一家配好且允许自动 > 当场问)。多个内置提供方时,
  「内置」按契约给的顺序挑第一个跑得起来的(降噪另有「不顺手去掉音乐」的约束,由契约的挑选钩子表达);
- **试一下**:给一个最小输入跑一次(一份文档、一段音频、一句话),结果怎么给人看;
- **实例变动钩子 / 清单**(原 `host_capabilities` 那两样):可选。那张表并进来,只剩一张。

生成保持 ADR 0020 的连接 + 模型机制 —— 它的挑选单位是模型不是提供方 —— 能力表里登记它,只为了「用在哪」和
插件页的展示,挑法不变。

### 2. 进程全局的引擎注册表退场

`get_denoise_adapter(engine)`、`get_separation_adapter(engine)`、`engine_catalog.describe_engines`、翻译里的
`if engine == "ai"`、转写里的引擎开关,统一换成 `capabilities.pick(db, owner, 能力, provider_id)` → 提供方 → 适配器。
一次改完调用方,**不保留老入口**(见 CONVENTIONS「不写兼容代码」)。

插件连接是**这个人的**:挑的时候带上是谁(工作流用运行者 `current_actor`,智能体用会话主人,界面用当前用户)。
共享工作区里别人的运行不会借用你的插件连接和密钥 —— 挑不到就按他自己的默认。

### 3. 「只经宿主」,不是「只给宿主」

> **已被 ADR 0033 取代**:认领调用类能力的工具是普通工具,智能体和工作流直接调它;宿主开放的是服务(素材进、文件出、进度),
> 能力是加在工具上的一份契约。下面保留当时的决定。

`HOST_ONLY_CAPABILITIES` 更名为 `HOST_PROTOCOL_CAPABILITIES`,意思说准:认领这些能力的工具说的是**宿主协议**
(文件进、文件出、进度、取消、记账),智能体和工作流不直接调插件工具 —— 那会绕开任务、用量台账和回执。
但**凡是宿主有入口用这项能力的地方,都能点名任何一家**:

- 工作流节点里挑实现的字段统一写 `options_from: "providers.<能力>"`(一个通用来源,不再每项能力写一个;
  节点里写死的 `options: [...]` 全部退场);
- 智能体工具的 `engine` / `parser` 参数按提供方的名字或 id 认(认不出就列出配好了的几家);
- 画板上的能力(降噪、分离、转写……)的引擎下拉同一个来源;
- 插件页上,只经宿主的工具列出来,能**试一下**。

新加入这个集合的能力:`audio_denoise`、`audio_separation`、`transcription`、`translation`、`speech_synthesis`
(连同已有的 `generation`、`tools`、`document_parse`)。装的那一刻照旧检查:进程插件、恰好一个工具认领。
`provides` 仍是开放词表:宿主不认识的能力照样装得上,插件页说清「这个版本的 Mosael 还用不到它」。

### 4. 「用在哪」现算,不手写

能力表不认识任何消费方;消费方在组装根(`app.main._wire_seams`)把自己登记进来,和能力表本身同一个手法:

- **工作流 / 画板**:不用登记 —— 扫 `NODE_TYPES`,字段 `options_from == "providers.<能力>"` 的节点就是;
- **智能体**:工具注册时声明 `capability`(确认式工具的 `ConfirmableTool.capability`、只读工具的同名标注),扫注册表;
- **宿主界面入口**(文档详情「重新解析」、配音库、素材库的降噪 / 分离、导入时自动解析……):各自领域登记一条
  `Use(capability, label_key)`。

插件页(每个只经宿主的工具下面)和设置页「能力提供方」(每项能力下面)照这份列出。

### 5. 设置页「能力提供方」是每项能力的总览

每项能力一块:候选(内置的、插件的,各自缺什么)、他定的默认、不定时会用哪家、用在哪。插件市场可以按能力筛选
(「谁能做降噪」)。

## 分步落地

1. **基础设施 + 文档解析**:`Capability` 加用在哪 / 试一下 / 多内置提供方;`providers.<能力>` 通用选项来源(文档解析
   先改过去);三种「用在哪」的登记;插件页宿主工具的「用在哪」现算、「试一下」;`host_capabilities` 并入能力表。
2. **降噪、分离人声**:契约 + 插件协议(一段音频进,一段 / 两段音频出)+ 内置引擎登记为提供方 + 节点 `engine` 字段
   改为 `providers.*`。存着的工作流里的 `auto` 用迁移改成空(= 按默认挑),其余值本来就是内置提供方的 id,原样有效。
3. **转写、翻译**:同上;翻译的「对话模型」提供方带着连接 / 模型两个参数。
4. **配音**:`engine_catalog` 收进能力表,音色清单是提供方的清单钩子。
5. **设置页总览、市场按能力筛选**。

进度:第 1 步已落地 ——「`host_capabilities` 并入能力表」:生成、工具清单作为不参与挑选的两项(`pickable=False`)
登记进能力表,实例变动的对齐钩子与插件页的清单挂在表里(`on_instance_change` / `listing`),`host_capabilities`
只剩按表查钩子、转发通知(查法由组装根注入,插件域不 import 能力表);(插件页宿主工具的「用在哪」由接口现算、文档解析 / 降噪 /
分离能在插件页「试一下」,走的是宿主真实的入口);第 2 步已落地;第 3 步的转写已落地(`transcription`:本机 FunASR / WhisperX 是内置提供方,素材转写、听写、
参考音频识别、工作流节点走同一个 transcriber;部署配置 `asr_provider` 不再参与挑选),翻译已落地(`translation`:`builtin:google` / `builtin:chat` 加插件,
对话模型那一家带连接 / 模型两个参数,节点里 `active_when: {engine: builtin:chat}`;剪辑页字幕翻译的引擎下拉照能力表列);第 4 步已落地(`speech`:内置引擎 id 统一成 `builtin:<适配器名>`,
存量数据由迁移改写;配音**没有默认**,`Capability.defaultable=False`,设置页只列候选和用在哪;内置实现的就绪判定带着人
`ready(db, owner)`,要钥匙的看他自己配没配好;插件协议 `op: voices / speak`);第 5 步的设置页总览已落地(每项能力一块:几家候选
并列可选、没配好的逐条说缺什么、「用在哪」),市场按能力筛选已落地:`provides` 能写的每一项由后端词表
`capabilities.vocabulary()` 给名字和「用在哪」(能力表各项 + 生成、工具清单),`GET /api/plugins/capabilities`;
市场按它筛、详情照它说,设置每项能力有「去插件市场找」直达筛好的市场;前端不再手写能力的名字。

每一步单独提交、门禁全过再推;插件协议写进 `docs/PLUGIN_MANIFEST.md`,随包的示例插件跟着补。

## 不做

- ~~不把插件工具直接开放给智能体和工作流(协议是宿主的,理由见 3)~~ —— 已被 ADR 0033 推翻;
- 不为旧入口留兼容层;旧数据用迁移。
