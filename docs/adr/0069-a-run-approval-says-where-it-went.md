# ADR 0069:「等人确认」说得出自己发到飞书没有 —— 投递结果落库、发不出去时站内再喊一声、结束时收回那张卡

## Status

Accepted — 2026-10-16。补的是 ADR 0064 / ADR 0066 定下的那张卡**发出去之后**的事:发没发到要看得见;
这一次等待结束(取消 / 超时)之后,飞书群里不该留一张还能点的死卡。ADR 0066 §3 那条
「降级成站内 + 日志里说清为什么没发」在这里**收紧**:降级照旧,**结果要落库**,发不出去还要在站内再喊一声。

## Context

### 「发到飞书没有」此前只活在日志里

`announce()` 先写站内通知(无条件),再尽力发飞书卡片;卡片失败退成一段文字;两层都失败(断网、
机器人没权限)只记一条日志。于是三件**完全不同**的事在记录里长得一模一样:

1. **真发到了**;
2. **这次本来就没打算发**:节点上写了「仅站内」,或工作区没有机器人、发起人没绑飞书;
3. **发失败了**。

单子上看不出是哪一种,而站内那条通知还会照旧写「在飞书里点卡片,或在应用的运行记录里点都可以」——
用户于是在飞书群里等一张**永远不会来的卡**,而没有任何东西会告诉他。

### 取消 / 超时之后,那张卡留在原地

取消本身已经接好了(`cancel_for_job` 和取消在**同一个事务**里把单置 `cancelled`),但飞书里那张卡
**没有主人**:留在群里、按钮还点得动,点了才报错。群里其他人不知道这件事已经结束。

### 「不存 message_id」那条理由,只对工具确认卡成立

`integrations/feishu/cards.py` 写着:「卡片回调允许在响应里直接返回一张新卡片,飞书会就地替换原卡。
所以『批准后把卡更新成结果态』不需要我们记住 message_id,也就不必给 ToolConfirmation 加列。」
那套做法**前提是点击者还在回调那条线上**。取消和超时没有一个"正在点的回调"可以搭车 ——
要把那张卡换掉,只能拿着消息 id 去 PATCH(`im/v1/messages/:message_id`)。

## Decision

### 1. 投递结果写进那张单(三列,一次迁移)

`workflow_run_approvals` 加:

- `feishu_delivery`:`sent` / `failed` / `not_attempted`(空 = 这一版之前建的,没有记录);
- `feishu_delivery_reason`:`not_attempted` 记**路由那一档的原因**(`none` / `no-bot` / `no-origin` /
  `not-bound` / `no-target`,`domain/feishu/routing` 早就给得出),`failed` 记发出去时撞上的那一句;
- `feishu_message_id`:发出去那条消息的 id(`om_…`)。

**三层降级里的第二层成了就算 `sent`**:飞书里的人确实收到了东西(item ①)。**`not_attempted` 不是失败**:
那是用户明说的选择(「仅站内」)或这次运行没有可发的去处 —— 记成失败,下一步就会有人给它加"重试"。
老行三列留空,不猜着回填:那三列路由只说明"当时解到了哪",发卡成没成当时根本没记。

### 2. 发失败就在站内再喊一声

`failed` 时除了既有的「在等人确认」,**再写一条**站内通知:说清"只能在站内批",带上那张单的 id
(payload 里也带,界面据此认出是哪一件事)。应用内那张审批卡上显示同一句 —— 而原来那句
「在飞书里点那张卡也一样」**只在 `sent` 时才说**,否则就是把人支去一个什么都没有的地方。

### 3. 结束时把那张卡收回,而且**在落库之后**

取消 / 超时时,若 `feishu_message_id` 非空,就把那条消息**就地换掉**(换成 `cards.settled_approval_card`
的结果态:已取消 / 超时,按钮没了);换不掉(降级发出去的是纯文字消息,卡片 PATCH 不了)就在**同一个会话**
里补一条文字。没发出去过就跳过,不报错。

**顺序是有意的**:撤单 / 落超时是同一个事务里立刻完成的(取消必须是第一优先),收回那张卡登记成
`after_commit` —— 一个已经过期的门不该有能力把"它被撤销了"这个结果弄回去。收回那一步整段包住,
失败只记日志。

### 4. 两条缝,方向仍然是"飞书认识领域"

领域只决定**什么时候**要收(`retire_feishu_card` 判有没有消息 id),怎么改那条消息住在集成层:
`use_run_card_settler`(`domain/workflows/approvals`)在组装根登记
`integrations/feishu/approvals.settle_run_approval`,和 `use_run_card_sender` 同一道缝、同一个方向。
领域层不认识集成层 —— 连函数内的延迟导入也不行(`tests/test_import_layering`)。

`Transport` 协议相应多一个 `update_card`:"发一张卡"和"换掉那张卡"是同一个出网原语的两种用法。

## Consequences

- 「到底发到飞书没有」从日志变成数据:界面说得出三种状态和原因,取消 / 超时也照 `feishu_message_id` 决定
  要不要去收回。数据库版本 28 → 29(`migrate-workflow-run-approvals-record-their-delivery`,
  排在 `create-current-schema` 之前 —— `create_all` 不给已有的表加列)。
- **发不出去不影响这次运行**:照旧降级、照旧在等 —— ADR 0066 §3 那条取舍没有变,只是不再沉默。
- **取消 / 超时的结果不受收回那一步影响**:顺序是"先落库、后尽力通知",失败只进日志。
- 「仅站内」这条语义**没有被弄坏**:它记 `not_attempted` 而不是 `failed`,站内不喊"发失败了",
  卡片上也不会出现"重试"的意思。
- 应用内**自己**批下一条(飞书那张卡还在)不是这一版的范围:那种情况下点飞书那张卡会就地翻成结果态
  (既有的 `_handle_run_approval` 那条路),而不是报错。
