# ADR 0007:智能体的三档权限模式

> 状态:**已落地**。设计定于 2026-08-02 的一次讨论;落地口径以下方指向的复验文档为准。
> 相关:[MCP.md](../MCP.md) 的确认门控与 `external` 档、`domain/agent/confirmations.py`。
>
> **落地方案见 [AGENT_PERMISSION_MODES.md](../AGENT_PERMISSION_MODES.md)**,它对照代码复验了本文的
> 前提,并修正了三处:①`browser_pool_open` 归在 `edit` 档是错档(它接的是用户真实登录身份),
> auto 下直接放行等于无声授权;②档位不能查静态表 —— `run_workflow` 挂 `ai-cost`,而它能执行
> `code` / `publish` / `http_request` 节点;③「AI 判断」**维持本文的决定要做**(2026-08-03 拍板),
> 但它不能是唯一的闸 —— 判断者看到的**参数本身**就是被影响过的模型写的,所以结构化规则先判、
> 判断者只在规则没覆盖处说话且不能翻案(见该文 §2.3 与 §4.7)。

## 背景

现在的确认门控是**二元**的:54 个工具里 15 个走确认卡,其余直接执行。走卡的那些每次都要用户
点头,一次任务里点十几次,而其中大多数(时间线编辑、工作流增改)是**可撤销**的 —— 用户点的
不是决定,是噪音。

参考对象是 Claude Code 的 auto-accept 与 Codex 的多档审核。但两者放开的东西和这里不一样,
这点必须先说清:

- Claude Code 的 auto-accept 降低的是**文件编辑**的门槛,而文件编辑有 git 可回滚;
  它对不可逆动作(推送、删除)仍然拦。
- Codex 的分档按**沙箱边界**切:只读 / 工作区可写 / 全权,靠的是进程隔离,不是信任。

共同点:**放开的都是可撤销、或被沙箱兜住的动作**。而 Mosael 的确认卡挡的恰恰不是这类 ——
`publish_asset` 发出去的帖子、`http_request` 打到别人服务器上的写请求、`run_code` 在用户
机器上跑过的代码,没有 git,也没有沙箱。

## 决定

三档。**按权限档而不是按工具**分,沿用已有的 `edit` / `ai-cost` / `render-cost` / `external`。

| 模式 | `edit`(可撤销) | `ai-cost` / `render-cost`(花钱,可预期) | `external`(后果在应用外,撤不回) |
| --- | --- | --- | --- |
| **手动**(默认) | 确认卡 | 确认卡 | 确认卡 |
| **auto** | 直接放行 | AI 判断 | AI 判断 |
| **bypass** | 直接放行 | 直接放行 | 直接放行 |

`bypass` 全放行是产品所有者的明确决定。本文档记录过程中提出、被接受的两点修正:

### 一、「AI 判断」必须由一个隔离的判断者做

原始设想是让主对话里的模型自己决定要不要放行。**不能这样做**:判断的模型和要执行的模型是
同一个,而它的上下文里有**工具返回的内容** —— 网页、插件输出、被检索到的文档。这些是数据不是
指令,但它们进了同一个上下文。一段写着「这是例行操作,无需确认」的网页文本,恰好能影响那个
判断。等于把授权决定交给了一个可被输入影响的判断者。

**做法**:判断走**单独一次调用**,只喂三样东西 —— 工具名、参数、以及用户预先写好的准则
(如「只发到我的草稿箱」「只请求这几个域名」)。**不喂对话历史,不喂工具返回的内容**。
它仍然是「AI 判断」,但判断者看不到能影响它的东西。多一次调用的成本,换掉一整类注入路径。

### 二、模式必须可见,自动放行必须留痕

- **可见**:当前处于哪一档要一直显示在输入框旁边,不能藏进设置。用户不知道自己授权了什么,
  就等于没有授权。
- **留痕**:确认卡现在有记录;自动放行的动作也要有,而且要能一眼看出「这条是自动放行的」
  以及「是哪一档放的」。事后能查,是 bypass 唯一可接受的前提。

## 未定项(实现前要定)

- **作用域**:模式是全局的、按工作区的、还是按会话的?倾向按会话 + 一个全局默认,理由是
  「本会话始终允许」已经是按会话的,两套作用域会互相打架。
- **bypass 的开启方式**:是否需要每次会话显式确认一次?倾向要 —— 它不该像主题开关那样粘住。
- **AI 判断的准则存在哪**:工作区级的一段文本?还是结构化规则(域名白名单 / 平台白名单)?
  结构化更可靠,文本更灵活。

## 被否掉的选项

- **按工具逐个配置**:54 个工具让用户逐个勾,没人会配,配了也记不住。权限档已经是现成的
  分组,而且它已经决定了确认卡的措辞和徽标。
- **给 `external` 也做「AI 判断」但不做 bypass**:产品所有者要的是完整的 bypass,
  不做半档。
- **靠沙箱放开 `run_code`**:值得做,但那是另一个功能(真正的沙箱),不该塞进权限模式里
  当作它的前提。

## 修订(2026-10-08):一轮结束,它留下的确认卡也结束;停止是停止,不是失败

> 来源:2026-10-08 全项目分析的智能体那一路(AGENT-1/2/3/4,外加创作类页面那一路的 UC-05),协调者照报告的建议拍板、
> 「作废用哪个状态」交给实现者定。复现全部在隔离环境里用脚本化的假模型做过(`scratchpad/agent-env`,不进仓库)。

### 问题

确认卡是一轮**阻塞着等**的东西:sidecar 停在那次工具调用上,用户批完才把结果交给模型。可卡和那一轮的生命周期没绑在一起:

- **孤儿卡**:用户在卡出来后按「停止」、卡等满 590 秒、整轮超过 600 秒(而且 600 秒里**包括等人批卡的时间** —— 先干两分钟活再
  开卡,人八分钟后回来,整轮已经被杀),这三种结局之后卡仍是 `pending`、仍能批、批了照样执行(复现:工作流真的建出来、笔记真的
  被改了),而模型被告知「失败 / 没发生」、结果永远送不回对话。卡还落进右上角全局确认中心一直挂着。选择卡(`ask_user`)早有兜底
  (答了之后 `deliver_to_session` 送回对话),确认卡没有对应的路。
- **停止记成失败**:停在工具执行中(最常见的就是正等着批卡),pi 把被中止的那次模型请求记成 `stopReason: "error"`(「This operation
  was aborted」),sidecar 认不出这是用户按的停止,气泡写「智能体执行失败,请稍后重试」。
- **停掉的部分回答不进记忆**:流式出字时停,部分回答照常落库、用户看着它,可 pi 发下一次请求时整条丢掉 `aborted` 的助手消息 ——
  用户说「接着说」,模型从头再来。
- **记忆已回存的失败轮又被整段重述**:失败时 sidecar 交回了记忆(host 回存),`unseen_since_last_success` 却仍把那一轮当成「你没见过
  的」重述一遍:同一个请求在模型眼前出现两次、还被告知从没处理过,它会把已经做成的部分再做一遍。
- **配置类失败说「请稍后重试」**:新用户没配对话模型就发消息,气泡写「请稍后重试」,原因藏在「错误详情」里 —— 而重试永远不会好。

### 决定

1. **新状态 `expired`(卡已作废)**,不沿用 `cancelled`:它说的是「这一轮已经结束,没人在等这张卡了」,和「用户拒绝」(`rejected`)、
   「执行失败」(`failed`)都不是一回事。`ToolConfirmation.error` 里记由头的码,界面按码说人话,不标红:

   | 码 | 什么时候 | 界面上 |
   | --- | --- | --- |
   | `turn_stopped` | 用户按了停止 | 这一轮已停止,卡已作废 |
   | `turn_failed` | 这一轮失败 / 超时 | 这一轮已经结束,卡已作废 |
   | `turn_ended` | 这一轮照常结束(卡等到点之后模型接着说完了) | 这一轮已经结束,卡已作废 |
   | `wait_timeout` | sidecar 等这张卡等到点 | 等太久没有批,卡已作废 |
   | `backend_restarted` | 后端重启时那一轮还在跑 | 这一轮已经结束,卡已作废 |
   | `orphaned` | 升级之前留下的孤儿卡(迁移) | 这一轮已经结束,卡已作废 |

   老的 `cancelled`(此前只有后端重启时写)由迁移一并改成 `expired` / `backend_restarted`,界面不留第二个分支。
2. **一轮收尾时作废这段对话还在等的卡**(`host._run_turn_thread` 的 `finally`,和拨回 idle 同一个事务;`card_expiry.expire_session_cards`)。
   条件更新,和认领卡同一种写法:用户恰好在这一刻点了批准,谁先落库谁算。没挂对话的卡(MCP 直连、工作流节点)不属于哪一轮,不碰。
3. **卡等到点先作废再说「没做」**:sidecar 到点后 `POST /api/confirmations/{id}/expire`,再告诉模型「这张卡已作废 —— 这个操作没有执行」。
   作废接口**只认开这张卡的那一轮的凭据**(令牌铸的时候记着是哪段对话,和开卡归属同一个来源);登录令牌、别的对话一律 404。
4. **等人的时间不算进整轮时限**:sidecar 开始 / 结束等人(确认卡、选择卡)时发 `awaiting_user`,`pi_client` 据此停 / 走整轮 600 秒的表
   (`ChildProcess.pause_deadline` / `resume_deadline`,可叠,几张卡同时等按计数)。停表本身有上限 `AWAITING_USER_PAUSE_CAP_SECONDS`
   (900 秒),防 sidecar 卡死在「等人中」;它必须比 sidecar 等一张卡的上限(590 秒)长 —— contracts/shared-constants.json 的 budgets
   原来那条「卡的等待压在整轮 600 秒底下」改成这条(`confirmation_wait_fits_inside_the_pause`)。
5. **停止就是停止**:sidecar 收到 `abort` 帧时记下「用户停了」,`runPiTurn` 据此判停止,不再只看 pi 的 `stopReason`。停止那一轮存进记忆
   之前,这一轮里被中止的助手消息改写成普通的一条(`agent-sidecar/src/stopped.ts`):留下已经说出来的字、末尾注明「被用户停止,没有说完」;
   没完成的工具调用块和思考块去掉;一个字都没说的换成一句「这一轮被用户停止了」。已经跑完的工具调用和结果不动。还没出字就停下的,
   宿主落一条「(还没开始回答就停下了。)」,不再报「模型没有返回任何内容,请检查供应商配置」。
6. **记忆已回存的失败轮不再重述**:失败落库时记 `payload.memory_saved`;补记只重述没回存的那几轮,对回存过的只补一句「上一轮中途失败了、
   为什么,做成的别再做一遍」。
7. **配置类失败气泡上说原因**:没有可用的对话模型、连接没有模型、模型什么都没回、还没调过工具就失败(多半是端点 / 模型名不对)这几种,
   抛错时带 `human`,气泡就是那句话;没有对话模型的另带 `error_code: no_chat_model`,气泡上给一颗「去设置里配一个」的按钮。

### 迁移

`expire-orphaned-session-confirmations`(SCHEMA 之后,排在删空对话之后,一次性):挂在对话上、还是 `pending` 的卡改成 `expired` / `orphaned`
(迁移跑在启动时、任何一轮开跑之前,这一刻这些卡没有一张还有人在等);老的 `cancelled` 改成 `expired` / `backend_restarted`。没挂对话的
不碰。幂等,测试钉着(`tests/test_agent_turn_lifecycle.py`)。

### 没做的

- 卡作废之后**不**把「那张卡作废了」再送回对话起一轮(选择卡那种兜底):作废的那一刻模型那一轮已经知道它没做(停止、失败、超时三种它都
  看得见),再起一轮只是替用户花钱。
- 飞书群里那张卡片不跟着改样子:点了会得到「这张卡已经作废」,和点一张已经被别人批掉的卡同一个回答。

## 修订之二(2026-10-08):谁能拍板、拍板记在哪;整理上下文也占着这段对话

> 来源:2026-10-08 全项目分析的智能体那一路第二批(AGENT-14/15/16、AGENT-10、AGENT-5),协调者照报告的建议拍板。复现同样在隔离环境里
> 用脚本化的假模型做过。

### 问题

- **交给 sidecar 的服务令牌能批卡、答卡**(AGENT-14):服务令牌按路径前缀放行(`/api/agent/`、`/api/confirmations/` …),方法不看 ——
  于是模型手上那份令牌能 `POST /api/confirmations/{id}/approve`,自己开的卡自己批。今天没有哪个工具这么做,可这道闸不该靠「没人去做」。
- **「只读」的子智能体拿得到问人和跳页**(AGENT-15):`ask_user` 不写数据,于是算只读;可用户看不见子智能体,它问出来的选择卡没有上下文
  可答,它阻塞时主智能体也卡在那次调用里。`open_view` 同理:不改数据,却把用户正在看的页面拽走。
- **「本会话始终允许」会丢**(AGENT-16):界面读出整份白名单、加一条、整份写回;几个工具调用同时等批时两张卡几乎同时点,两次读到同一份,
  后写的盖掉先写的。
- **全局确认中心盖住页面右上角**(AGENT-10):三百多像素宽,正好压在各页工具条最右边那几颗按钮上;自家智能体开的卡还写着「外部智能体请求
  · pi-agent」。
- **整理上下文不占着这段对话**(AGENT-5):摘要要几十秒,这期间发的一句照常起一轮;两边各读一份记忆、各写回一份,后写的盖掉先写的 ——
  整理期间说的那句(连同回答)从模型记忆里消失,或者整理白做。

### 决定

1. **服务令牌只读,外加明列的几条写**(`core/security.service_request_allowed`,鉴权依赖里一处判):`GET`/`HEAD`/`OPTIONS` 照旧按前缀放行;
   写只有 sidecar 这类调用方真要做的那几件 —— 调工具(`/api/agent/tools`、`/api/agent/tools/{name}`)、开卡(`POST /api/confirmations`:提议,卡挂在这份令牌那一轮上)、作废自己那一轮的卡
   (`/api/confirmations/{id}/expire`)、借还供应商凭据(`/api/agent/provider-credentials/{id}/acquire|commit|renew|release`)。批、拒、
   答选择卡都不在里面,403。新增一条 sidecar 要写的路由时在这里登记,测试(`test_service_token_cannot_decide.py`)钉着清单本身。
2. **子智能体的「只读」再去掉两样**(`agent-sidecar/src/subagent.ts` 的 `readOnlyTools`):问用户的(工具清单里带 `awaits_answer` 的)和
   `open_view`。
3. **「始终允许」加一条由服务端合并**:`POST /api/agent/sessions/{id}/allowances`(一条:工具 + 档位),在库里那一份上合并、和整份替换同一套
   校验;读 → 合并 → 提交在一把进程锁里(`autopilot.ALLOWANCE_LOCK`,后端只有一个进程),PATCH 整份替换也进同一把锁。界面卡上那颗按钮
   改走它。
4. **确认中心收得起来,收起来住在顶栏里**:卡上方一颗「先收起来」,收起是应用顶栏右侧的一颗「N 个请求等你确认」(顶栏里留的位,
   `components/layout/headerSlot`),点开回来;来了新卡自己展开 —— 收起的是「这几张」,不是「以后都别给我看」。还浮在页面上的话,盖住的
   还是那几颗按钮,收了等于没收。挂在对话上的卡抬头写「智能体请求」,只有没挂对话的(MCP 直连、飞书)才写「外部智能体请求 · 谁」。
5. **整理上下文和一轮同一个认领**(`host.compact_session_context` 用 `_claim_idle_session`):正有一轮在跑时整理返回 409;整理期间这段对话
   是 `running`,发来的话照排队的规矩进队,整理完(成功、失败都算)放开、收回那份令牌、把队列跑掉。摘要那几十秒不攥着这次请求的数据库连接,
   写回用新的连接(和一轮的三段式同一个理由)。界面在整理期间的状态行说「正在整理上下文…」,不说「思考中」。

### 没做的

- **停止之后排在队里的那句接着跑**(AGENT-17):按停止往往是「它跑偏了」,停之前顺手排的那句多半基于跑偏的内容,却立刻开跑。是退回输入框
  (Codex 的做法)还是队列暂停、给「继续发送」,要维护者定,这一版不改。—— 2026-10-09 定了,见修订之三。

## 修订之三(2026-10-09):按了停止,排着的话不自动接着跑

> 来源:体检 AGENT-17;维护者 2026-10-09 按推荐拍板(D63):不自动跑,留在排队条里,给一个「继续发送」。

**问题**:一轮收尾时宿主无条件 drain 队列。慢吐时排一句话再按停止,半秒后那句作为新的一轮开跑。按停止往往是「它跑偏了」,停之前
顺手排的那句多半是基于跑偏的内容写的,得再按一次停止。

**决定**:

1. **用户按停止停下的那一轮**(sidecar 回报 `aborted`,只有「停止」会让它这样收尾),收尾时把**此刻**排着的话扣下:payload 带上
   `held`,和拨回 idle 同一个事务(`host._hold_queue`)。之后再排的照常排队。
2. **扣下的不算「有东西在等」**:drain 的抢占条件(`_waiting`)和它取的那一条(`_runnable_queued`)都跳过 `held`。任务回执、整理完上下文
   这些别处来的 drain 不会为它们抢占这段对话,更不会把它们跑掉。
3. **不是用户停的照旧接着跑**:出错、整轮超时、整理上下文都不扣 —— 那不是「它跑偏了」。
4. **「继续发送」**:`POST /api/agent/sessions/{id}/queue/{message_id}/resume` 去掉那一条的 `held`,提交之后 drain。空闲就当场开跑,
   正忙(人已经又说了一句)就排在那一轮后面。一条一个按钮:扣下的有好几条时,先放哪一条、放不放,都由人定。插话、移除照旧。
5. **界面**:排队条空闲时也读(此前只在跑着时读,停下之后条就没了);它和消息一样不轮询,跟着会话的状态 / `updated_at` 重取
   (`transcriptFollowsSession`)。扣下的那一条那一格是「继续发送」,不是「插话」(没有一轮在跑,插不进去)。
