# ADR 0071:审批往返说的是**哪一张单** —— 决定一路带着单 id、现场没落就不列单也不让人决定、并行两道门开跑前拦下

## Status

Accepted — 2026-10-17。补的是 ADR 0064(「等人确认」:可持久化的暂停与恢复)与 ADR 0066(节点上写明
`channel` / `bot` / `to`)、ADR 0069(投递结果落库、结束时收回那张卡)**三份都定下之后**,一次往返
真正跑起来才暴露出来的那一族问题。**语义一条都没改**,改的是"这一次唤醒说的是哪张单""这一刻能不能
让人决定""两道门能不能同时活着"。ADR 0069 §4 末尾那条「应用内自己批下一条不是这一版的范围」
在本文档 §4 里补上。

## Context

一次运行里可以有好几张单(图里串着两道门),而唤醒、列表、超时、恢复各自都要说出"是哪一张"。
ADR 0064 的 `wake()` 只排 `job_id`,`_resumable(job_id)` 取"最早那张有检查点" —— 于是:

1. **批第二道门时,恢复用的是第一道门的现场**,两道门之间的节点**重跑一遍**,而任务照样报
   `succeeded`(重跑被成功掩盖)。实测:某个下游节点建了两行行、按次计费的那一步付了两次。
2. **单是先落库的、检查点后落**(执行器必须比卡片先落库,现场要等还在飞的兄弟节点各自落定)。
   这段窗口里批它:决定赢、运行永远停在 `running` —— 没有现场可恢复,谁也没法把它叫醒。
   同一段窗口里还会给群里发一张"已经被批过"的卡。
3. **并行分支上两个 `await_approval`**:引擎一轮只停得下**一个**暂停点,兄弟节点那边再抛一个
   同样的事就被当成**失败**(`error` 一落下整轮 failed)—— 这次运行判失败,而两张单都是 `pending`
   + 空检查点,永远挂在待批列表上:点了什么都不会发生,错误文本还是内部串
   `awaiting approval <hex> at node <id>`。
4. **应用内批的那一下,飞书那张卡留在原地**:两个按钮还点得动,群里别人以为这件事还欠着。
5. **重启接回会再说一遍**:引擎重新进到暂停那一步,于是第二条站内通知 + 第二张卡,而且新的消息 id
   覆盖旧的 —— 群里那张旧卡从此收不回来。
6. **应用内做的决定不收回飞书卡**(同 4);`on_timeout=remind` **只发站内**,飞书那边一个字都没有。

## Decision

### 1. "哪一张单"必须一路传下去,而且两条路的默认不同

`wake()` 把 `approval.id` 传下去;`dispatch_resume(job_id, approval_id=)` 给 id 就认**那一张**。
不给 id 时认的是**最新**那一张 —— 那是**重启接回**那条路:眼前那道门就是最后停下的那道。
**两条路的意图不同,合成一个默认值必然错一条**,所以它是个显式参数(`_resumable(..., approval_id=)`)。

### 2. 现场没落库的单:**不列、不让人决定**,引擎写完现场自己复查

两处一起堵:

- `approvals.ready_to_decide(row)`(**有 `checkpoint` 才算**);三个 `pending_for_*(job / workspace /
  workflow)` 与 `expire_due` 都按它过滤。零新 key、零 API 漂移 —— 前端那 5 秒轮询的窗口里没有可点的
  按钮,而不是点下去没反应。
- `engine._park_at_approval` 写完检查点**复查**这道门是不是已经被决定了(`db.refresh(approval)`,
  `status != PENDING`):是就**别再喊人来等**(那张卡会是一张"已经批过"的卡),**并在同一个事务里
  自己再排一次恢复**(`after_commit(dispatch_resume(job_id, approval_id=))`)。

### 3. 并行两道门:**开跑前**拦下(`run_preflights`)

判据用的是"这两个门会不会被**同时调度**",比对字面规则更严一点(有意):**互相不可达**是必要条件,
但还不够 —— 条件节点真 / 假两条出口上的两个门**永远不会同时活**(调度那一层按出口跳过没走到的那一支,
见 `engine.incoming_active`),那种图今天跑得起来,字面规则会误拦。所以还要排除
`_branch_apart`(被同一个会分支的节点分到两条互斥出口上)。

拦下的文案是 `wfErr_awaitApprovalParallel`(`core/messages/workflows.py`),说清是哪两个节点、
以及改法(串成一条线,或者先只留一个门)。放在和"循环体 / 子图里的门放不下"
(`wfErr_awaitApprovalNested`)同一处 —— `executors/approval.py` 的 `register_preflight`。

### 4. 应用内的决定**也收回飞书那张卡**

`decide_and_wake(via=...)`:赢下 CAS 之后,`via != "feishu"` 时 `after_commit` 调
`retire_feishu_card`。`via == "feishu"` 跳过 —— 那条路的**回调响应本身**就是把这张卡换成结果态
(ADR 0069 §4),再收一次是多余的。
这里补上了 ADR 0069 §4 末尾那条"不是这一版范围":现在两处点哪个都算数,卡片都跟着结果走。

### 5. 重启接回:同一个等待**只说一遍**,消息 id **不覆盖**

`announce()` 开头:已经有投递记录(`feishu_delivery` 或 `feishu_message_id` 非空)就**只更新现场、
不再说第二遍**。空着(第一次暂停、或上次还没说到就跑挂了)才说。
`_record_delivery` 写 `feishu_message_id` 时**最早那张的 id 不覆盖**:取消 / 超时照它去收群里那张卡,
后来真又发出去过一张的话,至少原来那张收得回来 —— 覆盖掉就是"发了两张,一张也收不回来"。

### 6. `on_timeout=remind` **也在飞书提醒**,而且**不换那张卡**

`settle_run_approval(outcome="remind")` 走同一个原语,但行为刻意不同:**在同一个会话补一句**
(「这件事还在等你确认,已经提醒过一次了 —— 决定权还在你手上」),**不把卡换掉** ——
`settled_approval_card` 生成的卡**没有按钮**,门还开着却把按钮拿掉比不提醒更糟。
没发出去过就跳过,失败只记日志,不影响"已提醒"这个已经落库的结果。

`remind` 还补了一条 CAS(与人的决定撞上时不再多喊一条自相矛盾的"还在等")。降级文案里
**去掉了"或在飞书里回复"** —— 全仓没有任何一条路把飞书里的回复变成决定(只有卡片上的按钮是),
那句话把人支去一个不存在的入口。

### 7. 一次等待只派一次恢复

`approvals._RESUMED`(per(运行, 单)的进程内标记)+ `resume_finished(job_id)`(引擎在接回来的那条
线程收尾时放下)。挡住的是"同一个等待被两条唤醒路各派一遍"(人的决定与重启 resumer 在毫秒级窗口里
撞上),而那时**库里还没有任何可写的状态** —— 所以它只能住在进程内,且登记在
[`docs/PROCESS_STATE.md`](../PROCESS_STATE.md)(起第二个后端进程时这一条要跟着一起想)。

## Consequences

- **多道门不再重跑中间节点**:批第二道门就从第二道门的现场接着跑。实测
  `project_create` 3 → 2 行、`makeB` 2 → 1 次、`gate1` 3 → 2 次(一遍停下、一遍读决定)。
- **那 5 秒轮询窗口里没有假的按钮**:单在、现场不在时列表根本不列它 —— 界面上"看得见就能点"这条
  性质保住了,代价是那一段窗口里这道门"还没出现"。
- **并行两道门从"跑到一半才失败"变成"开跑前拦下"**:代价是**条件节点的真 / 假两支照旧放行**这件事
  得靠 `_branch_apart` 判,而那是"会不会同时调度"这个更细的判据,不是图论上的可达性。
- **`remind` 在飞书里看得见**:一个门禁悄悄过期等于没装,ADR 0064 §6 那条"三种都再通知一次"现在
  在飞书那一侧也成立。**但那张卡不能换** —— 换掉就等于把还开着的门关上。
- **`_RESUMED` 是进程内的**:多进程下同一次等待可能被两个进程各派一遍。当前部署是单后端进程
  (见 PROCESS_STATE 第一节),真要起第二个时这一条要一起想。

## 验收

`backend/tests/test_await_approval_resume_gates.py`(13 条,HEAD 上 10 failed → 13 passed):

- **多道门各认各的现场**:批第二道门时,两道门之间的节点只跑一次;重启接回那条路另有一条测试钉着。
- **窗口期不可决定**:现场没落的单不出现在三个 `pending_for_*` 里,`expire_due` 也不动它;引擎写完
  现场复查到"已经决定了"时自己排一次恢复(决定赢了也醒得过来),且不再发第二张卡。
- **并行两道门**:开跑前 `wfErr_awaitApprovalParallel`;条件节点真 / 假两支上的两个门**照旧放行**。
- **应用内决定收回飞书卡**:`via != "feishu"` 时调用;`via == "feishu"` 时不重复收。
- **重启接回**:只有一条站内通知、只有一张卡,`feishu_message_id` 不被覆盖。
- **`remind`**:站内 + 飞书各说一声,卡**没有**被换(门还开着,`expires_at` 往后推一格)。
