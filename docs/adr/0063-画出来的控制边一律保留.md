# ADR 0063:画出来的控制边一律保留 —— 折边不再由规范化替作者做主

## Status

Accepted — 2026-10-16。维护者拍板:**方案 1 —— 画出来的控制边一律保留**(原话:「我要能看见 用方案一」)。
同一笔里给引擎补上「带路由语义的控制边优先」那半条规矩 —— 没有它,保留边会把几道门(开场为空就跳过出镜、
这一拍没有画外音就不铺音轨)当场废掉(§4)。

## Context

### 规范化在保存时替作者折边

`normalization.canonicalize_data_bindings` 干两件事:

1. 把精确引用 `{{节点.输出}}` 升级成显式**数据边**(这一步是对的,本文不动它);
2. 升级之后,把同一对节点间**没写 handle、来源也不分支**的控制边当多余的**折掉** —— 理由是"数据边也排先后"。

### 2026-10-16 的全模板只读审计

15 张官方模板**手写的图**里,`start → output` 的控制链本来都完整(**15/15**)。是第 2 步把它们折了:

| 量 | 数 |
| --- | --- |
| 控制链被折断的模板 | **10 / 15** |
| 被折掉的控制边(含循环体 / 子图,每张图) | **68 条** |
| 只剩数据入边、画布上那一格没有线的节点 | **55 个** |

为什么模板中招:模板用精确引用写取值 → 引用被升级成数据边 → 那一对进 `upgraded_pairs` → 作者画的顺序边
被当冗余折掉。

为什么"时有时无":折不折取决于**巧合**。`foldable_into` 要求「折掉后谁该跑不变」,目标另有入边时就不折。
最小复现:

```
start → A → T          每条都是普通控制边
T.body = "{{B.text}}"  于是 B → T 多出一根数据边
```

此时 `A → T` 被折掉(`upgraded_pairs` 命中、`T` 没有别的入边),`T` 只剩 `B → T` —— 同一张图里,
只要 `T` 再有**任何一条**别的入边,同一条 `A → T` 就留下。作者画的线在不在,取决于别处的连线。

### 引擎此前为什么"看着没事"

`engine.incoming_active`:有控制边只看控制边,任一条来源跑了就跑;一条控制边都没有才看数据边。
折边之所以历来"谁该跑不变",是因为折掉的那几条要么来源集合与数据边相同,要么目标另有条件的真 / 假出口 ——
**第二类其实会变**,只是变的方向正好是作者想要的那个方向(见 §4)。所以这个问题没有人当场发现:
画面上的线少了,跑出来的结果却是对的。

## Decision

### 1. 规范化只**加**边,一条都不折

`canonicalize_data_bindings` 删掉:`redundant` 那道过滤与它专用的辅助(`ordering_only` / `foldable_into` /
`routes` / `routing` / `control_into` / `upgraded_pairs` 与只为折边建的 `data_sources`)。**精确引用升级成
数据边本身照旧**,`new_bindings` 仍然用它追加边。

删除处留了注释说明为什么不再折(维护者的决定、「取决于巧合」的最小复现、引擎不受影响)。

### 2. 棘轮先红后绿

新增 `tests/test_drawn_control_edges_are_never_folded.py`,两条:

- **每张官方模板沿控制边从 `start` 走得到 `output`**(改之前 10/15 不可达);
- **规范化前后作者画的控制边一条不少**(改之前折 68 条),顺带钉住"数据边只增不减"。

判据走 app 自己的代码路径:模板建图函数里的 `normalize_graph` 换成原样交回取原图,再拿真
`normalize_graph` 比 —— 不手写第二套规则。`tests/test_official_templates_hold_together.py` 的
「两头都一定会跑的引用,画布上沿连线也是上游」跟着换成同一条引擎判法(见 §4)。

### 3. "谁该跑不变"这条判据原样保留

`tests/test_folding_control_edges_keeps_who_runs.py` 的场景一条没少,判据(谁在 context 里、谁不在)
逐字不变;变的只有「控制边在不在」—— 现在都在。另加一条:条件为真时,只挂在「假」出口上的目标**不跑**,
哪怕同格上那两条排先后的控制边的来源都跑了。

### 4. 引擎补上「带路由语义的控制边优先」(`engine.incoming_active`)

保留边之后,`engine.incoming_active` 的"任一条控制边来源跑了就跑"会把几道门废掉:

- 出镜版带货口播:`presenter → hook_talk` 是排先后的(值从 `{{presenter.entity_id}}` 的引用升级出来的
  数据边来),激活该由 `has_hook` 的「真」出口定。折边那会儿这条边已经不在,门是好的;保留之后
  `presenter` 必然跑 → `hook_talk` 必然跑 → 开场那句是空的时拿着空稿子去生成(真跑测试红了 5 条)。
- 同一类的还有 `pitch_project → hook_place`、`beat_on_timeline / beat_voice → beat_voice_place`
  (每一拍没有画外音就不铺音轨)、`narrate → place_voice`。

所以引擎按折边本来要达到的判法明说:

> 目标节点上有**带路由语义**的控制边(条件的真 / 假出口,或来源是会分支的节点)时,**由那几条定激活**。
> 同格上那些**已经有一条同向数据线**的普通控制边只定先后(数据线本身就在排先后,那条实线是画出来给人看的),
> 不激活它。一条带路由的都没有时,全部控制边照旧算数(一条控制边都没有,才看数据边)。

**"没有同向数据线"那一句不能省。** 折边只折"规范化刚为它补了一根数据线"的那些边;没有同向数据线的普通控制边,
折边从来不动它,它当时**是**在激活目标的。两条官方模板正靠它:

- `reference_video_shots` 的 `describe`:want_speech 的「真」出口经转写走到它,「假」出口直接到它,另有
  `transcript_section → describe`(没有同向数据线)。want_speech 为真时,若把最后那条也当成"只排先后",
  `describe` 不激活 → 报告、总结、交付整段不走。
- `highlight_shorts` 的 `cut_clips`:`has_clips` 的「真」出口 + `clips_project → cut_clips`(没有同向数据线)。

这**不是**新语义,是折边一直在模拟的那条语义的显式化:库里的每一张图都过过规范化,而规范化把"有同向数据线"
的那些边全折了,所以对**已存的图**这条改动观察不到;对新图,它让"折与不折"在「谁该跑」上完全等价。5 条真跑测试
(`tests/test_business_templates_really_run.py`)因此原样通过,一条断言都没放宽。

### 5. 代价一:已实例化的图**不会**被改写(这一条与最初的设想相反,是实测的)

一开始以为"用户侧已实例化的图会在下一次保存时长出控制边、`graph_hash` 变、看到合并 / 覆盖提示"。
**实测不是这样**:规范化只会**加数据边**(把精确引用升级),它从不凭空补一条控制边。所以:

- 一张旧图(库里那份本来就少了被折的几条边)打开、编辑、保存,**原样**——少的那几条不会长出来,
  `graph_hash` 也不变(实测:再存一遍,控制边还是那几条,hash 一模一样)。没有冲突提示,没有新修订,
  更没有数据损坏。这些图要拿到完整的连线,得「按新版重建」或从模板重新添加。
- 已安装的官方模板副本:启动时的 `_migrate_official_workflow_data_bindings` 重新规范化时 `normalized == graph`,
  不动它们(用户的改动保留 —— 那是可编辑副本)。
- **新建**、**按新版重建**、**恢复旧修订**拿到的都是新口径下那张完整的图(恢复走
  `normalize_graph(upgrade_graph(...))`,同样只会补数据边)。

换句话说:这一笔的收益是**从此以后**画出来的图都完整;已经画好的图不会被动手术。

### 6. 代价二:平行边会变多 → 前端**错开**(另一半的活,已由另一路落地)

同一对节点上现在可能同时有控制边与数据边(以前控制边被折掉,只剩数据边)。两条线会**重合**在一起。
这一笔**不动前端**;错开是另一路,已单独落地:`feat(canvas): 同一对节点之间的多条边走不同道次 —— 别让两根线
糊成一根`(见 `components/app/canvasEdgeShape.tsx`、`features/workflows/referenceHints.ts`)。那一版没落地之前,
画布上看到的是两条叠在一起的线;数据边是虚线、控制边是实线,颜色与线型仍分得开。

## 否掉的备选

- **只保留"折了会断链"的那些边**:等于把"取决于巧合"换成另一套巧合,作者仍然看不见自己画的东西。
- **写一条迁移,把已经存下来的图也补上那几条控制边**:图是用户的数据(用户可能已经改过、删过节点),
  成批改写会凭空多出一批修订;而且规范化本来就没有"补控制边"这个能力,要新写一份推断规则。收益只是让旧图
  也看得见,而旧图上的连线本来是**当时保存的那个样子**——不动它更诚实(§5)。
- **保留边但不改引擎,而是让模板作者把会破门的边删掉**:那 10 条边里有多条正是 `start → output` 链的一部分,
  删掉就把维护者要看见的链又弄断了;而且"作者画了又不算数"和折边是同一件事,只是换了个地方发生。

## 已知残留(留给下一笔)

1. **手画的"数据边 + 控制边"同一对节点,旁边又有条件出口时**:引擎按"与同向数据线重复的普通控制边只排先后"
   判,而折边当年只折"规范化刚补上数据线"的那些(用户自己画的数据线那对不折,见
   `test_control_edge_next_to_data_edge_survives_save.py`)。图里分不出这根数据线是谁画的,所以这一种形状下
   谁该跑与折边那会儿有一处差别。它要同时满足三件事(同一对节点上既有手画数据线、又有手画普通控制边、
   目标还有条件的出口),官方模板里一处都没有。
2. **就绪检查的静态分析还没跟上。** `graph_rules.never_run_nodes` / `analyze.ts` 的 `neverRunNodes` 仍按
   "任一条控制边都能让它跑"算(它们问的是"**可能**跑",故意把两支都算上)。上面那条新判法只在一种形状下比它
   更严:目标有条件出口、其余激活来源都各自配着数据线、而那个条件又一定不跑 —— 这种图编辑器不会再报「未连接到
   流程」,引擎却不会跑它。改它要**两边一起改**(前端 + 后端 + `contracts/workflow-never-run-cases.json`),
   所以没有塞进这一笔。

## Consequences

- 画布与库一致:作者画的控制边在库里、在官网下载的副本里、在画布上都在,不再被保存这一步悄悄改掉。
- 引擎多一条明写的判法(§4):同格上有条件的真 / 假出口时,一条普通控制边是否还能激活目标,取决于它有没有
  一条同向数据线 —— 这正是折边当年折掉的那一类。
- 官网副本 30 份(15 张 × 中英)按新口径重新导出:全部层级的边 **892 → 1028**(+136 = 每张图 68 条;
  顶层 +86 = 每张图 43 条)。
- 已实例化的旧图**不会**被改写:没有冲突提示、没有新修订、没有数据损坏(§5)。新画出来的图(新建 / 按新版
  重建 / 恢复旧修订)才带完整的连线;旧图要补上得走「按新版重建」。
- 前端平行边错开是接下来的活(§6)。
