# ADR 0008:两种部署,三类归属

> 状态:**已决定,未实现**。现状盘点见 [PERMISSION_MODEL.md](../PERMISSION_MODEL.md)(每条都跑过)。
> 本文推翻三个前提:「一套角色能表达所有权限」、「进了工作区就是大家的」,以及最要命的那个 ——
> **「后端总在用户自己的机器上」**。

## 0. 先纠正一个前提

这份文档的前两版都建立在「本地优先的桌面应用,后端跑在用户自己机器上」之上,并由此得出
「应用内权限拦不住机器主人,对他做校验是演戏」。

**那只对了一半。** 这个应用**支持分布式部署** —— 前端可以指向任意后端(设置页里就有「后端服务器·
切换」),`backend_host` 可配,`oauth_redirect_base` 的注释明写「团队部署时覆盖回调基址」,
`permissions.py` 自己也写着「on a team/remote backend it is not」。

所以有两种部署形态,而权限模型必须**按更难的那种来设计**,再退化到简单的那种:

| 形态 | 后端在哪 | 应用内权限是什么 |
| --- | --- | --- |
| **单机** | 用户自己的机器 | 便利,不是安全边界 —— 他本来就能打开数据库 |
| **共享后端** | 一台服务器,多人通过网络连 | **唯一的边界**。它失效 = 别人的数据、别人的钱、这台服务器 |

前两版按第一种设计,于是把「机器主人 = 第一个用户」当成理所当然。在第二种形态里,
**跑这个后端的人未必是任何一个用户**,而**任何能连到这个端口的人都不该被默认信任**。

### 0.1 按共享形态重新看,链条是这样的(已复现)

```
陌生人自助注册(库里已有用户)         -> 200
  立刻改实例级网络设置                -> 403
  自助新建一个工作区                  -> 200   ← 他在里面是 owner
  再改一次实例级网络设置              -> 200
  存一张含 code 节点的工作流          -> 200   ← 服务端执行任意 Python
  读 TTS 配置(含解释器路径)          -> 200
```

`/auth/register` **完全开放**:没有邀请制,不在引导完成后关闭,也没有任何部署级开关。于是在共享
后端上,「任何能连到这个端口的人」到「在这台服务器上执行任意代码」之间,只隔着一次注册和一次
新建工作区。

这不是某个接口写错了。是模型里**没有「这个部署归谁」这个概念** —— `ensure_instance_admin` 试图
用「在某处是 admin」去近似它,而在开放注册下,那个「某处」是可以自己造出来的。

承认这两种形态之后,要回答的问题有两个:**这个部署归谁**,以及**每一样东西是谁的**。

答案有三种,而现在的模型只表达得出第三种:

| 归属 | 是什么 | 现状 |
| --- | --- | --- |
| **部署的** | 这个后端实例:解释器路径、网络出口、插件、在服务端跑代码 | 用「在任意工作区里是 admin」近似,而工作区可以自助新建 —— 加上开放注册,等于**没有闸**(已复现) |
| **某人的** | 他的身份与他的钱:供应商密钥、发布账号、已登录的浏览器、他自己的对话 | **完全不存在**。这四类全部按工作区存,没有一张表有 `user_id`(已核) |
| **大家的** | 一起做的东西:素材、序列、工作流、知识库 | 表达得不错,35 张表按 `workspace_id` 隔开,不是成员一律 404 |

第二行是这次重想的核心。它此前被我写成「供应商凭据归人」的一条修复 —— 那是把通则当成了特例。

### 1.1 「某人的」不存在,后果是什么(已复现)

```
editor 列出 owner 的对话           -> ['owner 的私人对话']
editor 读 owner 对话里的消息        -> 200
viewer 取供应商的明文 OAuth 凭据    -> 200,响应里含 access token
```

`PublishAccount` 存的是某人在微博/B站的登录态,`BrowserProfile` 存的是某人已登录的浏览器 ——
同工作区的任何 editor 都能拿它们去发帖、去操作。这不是配置错了,是**这些东西压根没有主人这一栏**。

在共享后端上这一条的份量完全不同:单机形态下"另一个成员"通常不存在,而共享形态下他就在隔壁。

### 1.2 智能体是第四类主体,但它不需要第四种归属

它以某个人的身份行动,权限必须是那个人的子集。所以它不引入新的归属,只引入一条**恒等式**
(见 D5)。

## 2. 决定

### D1 「部署管理员」成为一等概念,并且**不靠自助获得**

`users.is_deployment_admin`。判据不再是「在某处是 admin」——那在开放注册下等于没有判据。

- **引导**:库里一个用户都没有时,第一个注册的账号成为部署管理员。这是自托管软件的通行做法
  (GitLab / Gitea / Grafana 都是这样),而且仓库里已有同一条理由的先例
  (`_adopt_orphan_workspaces`:第一个账号继承登录前建的工作区)。
- **引导之后注册即关闭**,只能由部署管理员发邀请。开放注册在单机形态下无害,在共享形态下是
  上面那条链的第一环 —— 而这两种形态用的是同一份代码,所以按更难的那种来。
  想保持开放的部署可以显式打开 `OPEN_STUDIO_OPEN_REGISTRATION`。
- 只有部署管理员能授予或收回这个身份。

`ensure_instance_admin` 改名 `ensure_deployment_admin` 并改判据。**不叫「宿主主人」**:在共享部署
里跑这个后端的人未必是任何一个用户,这个身份说的是「谁对这个部署负责」,不是「谁拥有这台机器」。

**部署级能力收成唯一一份清单**:TTS 解释器路径、网络代理、插件启用、ASR/TTS 模型下载、
工作流 `code` 节点、`run_code`、授予部署管理员本身。

### D1b 服务端执行代码要能被整体关掉

`code` 节点与 `run_code` 在单机形态下是「在我自己的机器上跑我自己的脚本」,在共享形态下是
**在别人的服务器上执行任意代码**。仅靠角色是不够的 —— 部署管理员这个身份可以被授予,而这项能力
的后果不在这个应用里。

所以给它一个**部署级开关**,默认按形态取值:绑在回环地址上默认开,绑在非回环地址(即对外提供
服务)默认关。想在共享部署上开的人必须显式开,并且在开的那一刻知道自己在开什么。

### D2 「某人的」东西加上主人,并且**默认不共享**

四张表加 `owner_user_id`,外加一张共享表:

```
publish_accounts   + owner_user_id      -- 他的微博/B站登录
browser_profiles   + owner_user_id      -- 他已登录的浏览器
agent_sessions     + owner_user_id      -- 他的对话
provider_credentials(user_id, profile_id)  -- 新表:他的密钥(从 provider_profiles 搬出来)

resource_shares(kind, resource_id, workspace_id, shared_by)   -- 主人显式共享进某个工作区
```

**归属与共享是两件事**,现在被压成了一件:今天「把东西放进工作区」既是存储方式,也是共享方式,
于是没有「放进来但仍然是我的」这种状态。分开之后,一条规则覆盖四类资源,不是四个特例。

默认私有。共享是主人的一次显式动作,可以撤回。**单机形态零感知** —— 只有一个人,他的东西就是他的;
共享形态下这一条才开始有分量。

`ProviderProfile` 留在实例级:它回答「怎么连到这家供应商」(端点、模型目录、定价规则),
那是配置,不是身份。凭据解析顺序:**自己的 → 部署管理员共享出来的 → 报「请先配置」**。

### D3 角色即权限,删掉权限位矩阵

身份类资源搬出工作区之后,权限位剩下的意义所剩无几:`credentials` 没有对应的能力了(配的是
自己的),`publish` 也是(用的是自己的账号)。而 `upload / edit / delete / export / schedule` 之间
的区分,在一个内容工作区里从来没有人真的分开配过。

所以:**只留角色,删掉 9 个权限位与 `WorkspaceMemberPerm` 整张表**。

```
viewer  读内容
editor  读写内容,可以用智能体
admin   editor + 改工作区设置、管成员
owner   admin + 删除/转让工作区
```

少一个概念,少一张表,少 24 处「这条路由该查哪个位」的判断。顺带解掉一个从没起过作用的条件:
`editor` 默认持有 `credentials`,于是 `ensure_instance_admin` 的第二个条件恒真。

**可逆**:真需要逐位配置时再加回来,那时会有真实用例说清楚要哪几位。

### D4 写权限显式化

`ensure_workspace_access` 靠一个只在 ASGI 中间件里绑的 ContextVar 判断该不该查写权限,默认
`"GET"`。它守着 43 条写路由;任何不经 HTTP 的调用(后台线程、队列、定时)拿到的都是默认值 ——
本轮已经在确认卡的批准路径上复现过一次(viewer 在后台线程里批准成功且真的执行了)。

拆成 `ensure_workspace_member`(读)与 `ensure_workspace_role(editor)`(写),逐条标注,改完删掉
那个 ContextVar。

### D5 智能体的权限恒等式

> **智能体能做的 = 行动人能做的 ∩ 这次对话授予的档位**

- **上界**:任何自动放行都必须经过与人工同一个 `authorize_*` 函数。bypass 绕过的是「用户同意」,
  不是「他有没有这个权限」。
- **下界**:三档模式只能收紧,不能放开行动人本来没有的东西。

两侧都用棘轮钉住 —— 下一个人加第二条批准路径时会红。

### D6 归属让确认卡的会话归属变干净

三档权限模式现在靠 `mode_set_by` 记「模式是谁开的」,因为 `AgentSession` 没有主人。有了
`owner_user_id` 之后这个字段可以退场:模式属于会话,会话属于人。

## 3. 迁移(按 [ADR 0006](0006-migrate-instead-of-branching.md):就地迁,读取期不留分支)

1. `users.is_deployment_admin` → 置给 `created_at` 最早的账号;注册随即转为邀请制
   (已经开着的部署可以用环境变量保持开放)。
2. 四张表补 `owner_user_id` → 回填成**该工作区的 owner**。他是当初建这些东西的人,或者至少是
   现在对它们负责的人。
3. `resource_shares` → 为每一条已存在的记录建一行「共享给它当前所在的工作区」。
   **升级前后行为完全一致**:今天大家都能看见的,升级后仍然看得见;从此以后新建的默认私有。
4. `provider_credentials` → 把 `ProviderProfile` 上的 `api_key` / `oauth_credential` 搬成部署管理员
   名下一行并标共享,然后删掉那三列。
5. `WorkspaceMemberPerm` 整张表删掉,`PERMS` 从代码里去掉。

五步都幂等,读取代码里不出现「有没有这一列」的分支。

## 4. 顺序

| # | 内容 | 影响面 | 前置 |
| --- | --- | --- | --- |
| 0 | **注册转邀请制 + 服务端执行代码的部署开关** | 小 | 无 |
| 1 | `is_deployment_admin` + `ensure_deployment_admin` + 部署能力清单 | 小:一列、一个函数、约 32 处改名 | 无 |
| 2 | 角色即权限:删权限位与整张表 | 中:24 处调用点 + 团队设置页 | 无 |
| 3 | 归属与共享:四张表 + `resource_shares` + 列表过滤 | **大**:触到发布、浏览器池、对话列表、素材可见性 | 1 |
| 4 | 凭据归人(第 3 步的一个实例) | 大:供应商解析、sidecar 下发、OAuth 刷新、额度 | 3 |
| 5 | 写权限显式化(43 条) | 中:机械 | 2 |
| 6 | 智能体恒等式的棘轮 | 小 | 1 |

**第 0 步先发**:它单独就把那条「陌生人 → 服务端执行代码」的链掐断在第一环,而且不依赖其余任何一步。
第 1、2 步互不依赖。**第 3 步之前不要动第 4 步** —— 凭据是归属的一个实例,先有通则
再落特例,否则会写出第二套只服务于供应商的共享机制。

## 5. 被否掉的选项

- **把供应商整个搬到工作区级**:同一个人在三个工作区里要配三次同一把钥匙,而钥匙是他的。
- **给 `ensure_instance_admin` 打补丁(比如"必须在默认工作区里是 admin")**:默认工作区可以被删、
  可以被转让,而且这只是把自助升级的入口换个地方 —— 仍然不是「机器主人」。
- **用配置文件里的 `admin_username` 表示部署管理员**:它在库外,和用户表会各说各话,改一次要重启;
  而这件事本来就该是数据。(但**开关**类的东西 —— 注册是否开放、服务端能不能跑代码 —— 留在配置里
  是对的:它们是部署的属性,不是某个人的属性。)
- **只按单机形态设计,共享形态"以后再说"**:两种形态用的是同一份代码,而"以后"意味着某个用户已经
  把后端绑在了 0.0.0.0 上。按更难的那种设计、退化到简单的那种,单机用户一点感知都没有。
- **只修供应商凭据,不动发布账号与浏览器档案**:那是把通则当特例,下一次同类资源出现时会再犯一遍
  (这正是本文第一版做的事)。
- **等到真有团队部署再说**:那时库里已经积着一堆按旧模型建的数据,而迁移难度正比于积压量。
