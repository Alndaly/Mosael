# ADR 0008:三类主体 —— 宿主主人、工作区成员、智能体

> 状态:**已决定,未实现**。现状盘点见 [PERMISSION_MODEL.md](../PERMISSION_MODEL.md)(每条都跑过)。
> 本文推翻的不是某个接口,是「用一套角色表达所有权限」这个前提。

## 1. 从头看:这个应用在防谁

Open Studio 是**本地优先的桌面应用**:后端跑在用户自己的机器上,数据在他自己的 SQLite 里。
这件事决定了一个常被绕过的事实 ——

**任何应用内的权限,都拦不住这台机器的主人。** 他可以直接打开数据库、可以改代码、可以杀进程。
对他做权限校验是在演戏。

所以真正要防的只有两个,加上一个新出现的:

| 主体 | 它是什么 | 边界在哪 |
| --- | --- | --- |
| **宿主主人** | 拥有这台机器的人 | 应用内**没有**边界 —— 承认这一点,别假装 |
| **工作区成员** | 通过网络连到这个后端的其他人 | 每一份资源都要按工作区隔开 |
| **智能体** | 以某个成员的身份行动,但会被它读到的内容影响 | 它的权限必须是**行动人权限的子集** |

现在的模型只有一套词汇(owner / admin / editor / viewer + 9 个权限位),用它去表达这三件事:

- 宿主主人 → 用「在任意工作区里是 admin」近似 —— 而人人都能新建工作区,所以这个近似是**自助的**
  (已复现:viewer 新建一个自己的工作区,就能改实例级网络设置)。
- 工作区成员 → 表达得不错,这一层是严的。
- 智能体 → 完全在另一套系统里(确认卡 / 三档模式),和权限位没有连接点。

**一层假的、一层真的、一层在别处。** 后面所有的对不上都是这一句的推论。

## 2. 决定

### D1 宿主主人是一等概念,不再靠角色近似

`users` 加 `is_host_owner`。**第一个注册的账号自动持有** —— 桌面应用里那就是机器的主人,而且
仓库里已经有同一条理由的先例(`_adopt_orphan_workspaces`:第一个账号继承登录前建的工作区)。
只有宿主主人能授予或收回它。

`ensure_instance_admin` 改名 `ensure_host_owner` 并改判据。名字里的 "instance admin" 承诺的
本来就是这个,只是实现没做到 —— 与其解释这个词,不如让它名副其实。

**宿主级能力只有一份清单**(在此之前它散在各处):
TTS 解释器路径、网络代理、插件启用、ASR/TTS 模型下载、工作流 `code` 节点、`run_code`、
以及授予宿主主人本身。

### D2 供应商:配置留在实例,**凭据归人**

`ProviderProfile` 回答的是「怎么连到这家供应商」—— 端点、模型目录、定价规则。它是配置,
共用没问题,留在实例级。

**密钥不是配置,是身份。** 新增 `ProviderCredential(user_id, profile_id, api_key | oauth_credential)`。

理由有三条,任意一条都够:

1. **谁付钱谁用**。团队后端上,Alice 的订阅被 Bob 的对话烧掉是错的,而今天就是这样。
2. **谁的账号谁看**。现在 `/agent/provider-credentials/{id}/acquire` 只要登录身份就返回明文
   OAuth 凭据 —— viewer 也能拿(已复现)。凭据归人之后这条**结构上不存在**:你只能读自己的。
3. **单机零感知**。一个人的安装里,第一个用户就是宿主主人,他配的就是他自己的,行为一模一样。

解析顺序:**行动人自己的凭据 → 宿主主人标记为共享的那份 → 都没有就报「请先配置」**。
共享是显式的一个开关,不是默认 —— 默认「我的钥匙是我的」。

### D3 `credentials` 这个权限位退场

它现在同时是三个东西:工作区权限位、`ensure_instance_admin` 的默认参数、插件凭据表的名字。
凭据归人之后,「能不能在工作区里配供应商」这件事不再存在(配的是自己的),这个位没有对应的能力了。

顺带解掉一个荒谬:`editor` 默认持有 `credentials`,于是 `ensure_instance_admin` 的第二个条件在
默认配置下恒真,判据只剩「角色 ≥ admin」——一个从来没起过作用的条件。

### D4 写权限显式化,不再靠「当前请求是不是 POST」

`ensure_workspace_access` 读一个只在 ASGI 中间件里绑的 ContextVar 来判断该不该查 `edit`,
默认 `"GET"`。它守着 43 条写路由。任何不经 HTTP 的调用(后台线程、队列、定时)拿到的都是默认值,
「写要 edit」那半条静默失效 —— 本轮已经在确认卡的批准路径上复现过一次(viewer 在后台线程里
批准成功并真的执行了)。

拆成两个不会误解的:`ensure_workspace_member`(读)、`ensure_workspace_perm(..., "edit")`(写)。
43 条逐条标注,机械但没有巧思。改完删掉那个 ContextVar —— 留着它就还会有人依赖它。

### D5 智能体的权限写成恒等式

> **智能体能做的 = 行动人能做的 ∩ 这次对话授予的档位**

两侧都要钉住:

- **上界**:任何自动放行都必须经过与人工同一个 `authorize_*` 函数(今天成立,但没有测试挡住
  第二条捷径出现)。bypass 绕过的是「用户同意」,不是「他有没有这个权限」。
- **下界**:三档模式只能**收紧**,不能放开行动人本来没有的东西。

这条本来就是设计意图,散在几处注释里。写成不变量 + 棘轮之后,下一个人加第二条批准路径时会红。

### D6 不做的

- **不给角色/权限位做大手术**。owner/admin/editor/viewer + 8 个位(去掉 credentials)表达工作区
  内的分工够用,换一套只是把同样的复杂度换个形状。
- **不做「多租户」**。这是本地优先的桌面应用,工作区是团队协作的单位,不是租户隔离的单位。
- **不试图在应用内约束宿主主人**。见 §1。

## 3. 数据模型改动

```
users
  + is_host_owner   BOOLEAN NOT NULL DEFAULT 0

provider_credentials                      -- 新表
    profile_id      → provider_profiles
    user_id         → users
    api_key         TEXT
    oauth_credential JSON
    shared          BOOLEAN NOT NULL DEFAULT 0   -- 宿主主人可把自己的这份共享给全体
    credential_version INTEGER
    UNIQUE(profile_id, user_id)

provider_profiles
  - api_key, oauth_credential, credential_version   -- 迁移之后删列

workspace_member_perms / roles
  - credentials 权限位                              -- 迁移之后删
```

## 4. 迁移(按 [ADR 0006](0006-migrate-instead-of-branching.md):就地迁,读取期不留分支)

1. `users.is_host_owner`:置给 `created_at` 最早的那个账号。一个人的安装里就是他自己;团队安装里
   是当初装这台后端的人 —— 两种情况下都是对的那个人。
2. `provider_credentials`:把现有 `ProviderProfile` 上的 `api_key` / `oauth_credential` 搬成宿主
   主人名下的一行,**并置 `shared=1`**。行为与升级前完全一致(所有人照旧能用),但从此以后新配的
   凭据默认属于配置者本人。搬完删掉原来那三列。
3. `credentials` 权限位:从 `PERMS` 里去掉,`workspace_member_perms` 里的对应行删掉。

三步都幂等,读取代码里不出现「有没有这一列」的分支。

## 5. 顺序与影响面

| # | 内容 | 影响面 | 能独立发 |
| --- | --- | --- | --- |
| 1 | `is_host_owner` + `ensure_host_owner` + 宿主能力清单 | 小:一列、一个函数、约 32 处调用点改名 | 能 |
| 2 | 凭据归人(新表 + 迁移 + 解析顺序 + 设置页) | **大**:触到供应商解析、sidecar 下发、OAuth 刷新、额度查询 | 依赖 1 |
| 3 | 写权限显式化(43 条) | 中:机械,但要逐条判断该用哪个权限位 | 能 |
| 4 | 智能体恒等式的棘轮 | 小 | 依赖 1 |

**第 1 步之前不要动第 2、4 步** —— 在「宿主主人」存在之前,收紧任何一处都只是把「谁能自助升级」
换个地方问一遍。

## 6. 被否掉的选项

- **把供应商整个搬到工作区级**:那样同一个人在三个工作区里要配三次同一把钥匙,而钥匙是他的、
  不是工作区的。凭据归人、配置留实例才对得上现实。
- **给 `ensure_instance_admin` 加一个"必须在默认工作区里是 admin"的补丁**:默认工作区可以被删、
  可以被转让,而且这只是把自助升级的入口从"新建工作区"换成"进默认工作区" —— 仍然不是「机器主人」。
- **用配置文件里的一个 `admin_username` 表示宿主主人**:它在库外,和用户表会各说各话;
  改一次要重启;而这件事本来就该是数据。
- **等到真有团队部署再说**:那时库里已经积着一堆按旧模型建的数据,而迁移的难度正比于积压量。
  现在改,迁移只有三步。
