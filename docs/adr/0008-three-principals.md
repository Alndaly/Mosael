# ADR 0008:三类归属 —— 宿主的、某人的、大家的

> 状态:**已决定,未实现**。现状盘点见 [PERMISSION_MODEL.md](../PERMISSION_MODEL.md)(每条都跑过)。
> 本文推翻的不是某个接口,是两个前提:「一套角色能表达所有权限」,以及「进了工作区就是大家的」。

## 1. 从头看

Open Studio 是**本地优先的桌面应用**:后端跑在用户自己的机器上,数据在他自己的 SQLite 里。
由此有一个常被绕过的事实 —— **任何应用内的权限都拦不住这台机器的主人**。他能直接打开数据库、
改代码、杀进程。对他做校验是演戏。

承认这一点之后,剩下要回答的其实只有一个问题:**每一样东西是谁的。**

答案有三种,而现在的模型只表达得出第三种:

| 归属 | 是什么 | 现状 |
| --- | --- | --- |
| **宿主的** | 这台机器:解释器路径、网络出口、插件、跑代码 | 用「在任意工作区里是 admin」近似 —— 而人人都能新建工作区,所以是**自助的**(已复现) |
| **某人的** | 他的身份与他的钱:供应商密钥、发布账号、已登录的浏览器、他自己的对话 | **完全不存在**。这四类全部按工作区存,没有一张表有 `user_id`(已核) |
| **大家的** | 一起做的东西:素材、序列、工作流、知识库 | 表达得不错,35 张表按 `workspace_id` 隔开,不是成员一律 404 |

第二行是这次重想的核心。它此前被我写成「供应商凭据归人」的一条修复 —— 那是把通则当成了特例。

### 1.1 「某人的」不存在,后果是什么(已复现)

```
editor 列出 owner 的对话           -> ['owner 的私人对话']
editor 读 owner 对话里的消息        -> 200
viewer 取供应商的明文 OAuth 凭据    -> 200,响应里含 access token
```

`PublishAccount` 存的是某人在微博/B站的登录态,`BrowserProfile` 存的是某人已登录的浏览器 ——
同工作区的任何 editor 都能拿它们去发帖、去操作。这不是配置错了,是**这些东西压根没有主人这一栏**。

### 1.2 智能体是第四类主体,但它不需要第四种归属

它以某个人的身份行动,权限必须是那个人的子集。所以它不引入新的归属,只引入一条**恒等式**
(见 D5)。

## 2. 决定

### D1 宿主主人成为一等概念

`users.is_host_owner`。**第一个注册的账号自动持有** —— 桌面应用里那就是机器的主人,而且仓库里
已有同一条理由的先例(`_adopt_orphan_workspaces`:第一个账号继承登录前建的工作区)。
只有宿主主人能授予或收回。

`ensure_instance_admin` 改名 `ensure_host_owner` 并改判据 —— 它的名字承诺的本来就是这个。
**宿主级能力收成唯一一份清单**:TTS 解释器路径、网络代理、插件启用、ASR/TTS 模型下载、
工作流 `code` 节点、`run_code`、授予宿主主人本身。

### D2 「某人的」东西加上主人,并且**默认不共享**

四张表加 `owner_user_id`,外加一张共享表:

```
publish_accounts   + owner_user_id      -- 他的微博/B站登录
browser_profiles   + owner_user_id      -- 他已登录的浏览器
agent_sessions     + owner_user_id      -- 他的对话
provider_credentials(user_id, profile_id)  -- 新表:他的密钥(从 provider_profiles 搬出来)

resource_shares(kind, resource_id, workspace_id, shared_by)   -- 主人显式共享进某个工作区
```

**归属与共享是两件事**,现在被压成了一件:今天「把东西放进工作区」既是存储方式,也是共享方式,
于是没有「放进来但仍然是我的」这种状态。分开之后,一条规则覆盖四类资源,不是四个特例。

默认私有。共享是主人的一次显式动作,可以撤回。单机安装零感知 —— 只有一个人,他的东西就是他的。

`ProviderProfile` 留在实例级:它回答「怎么连到这家供应商」(端点、模型目录、定价规则),
那是配置,不是身份。凭据解析顺序:**自己的 → 宿主主人共享出来的 → 报「请先配置」**。

### D3 角色即权限,删掉权限位矩阵

身份类资源搬出工作区之后,权限位剩下的意义所剩无几:`credentials` 没有对应的能力了(配的是
自己的),`publish` 也是(用的是自己的账号)。而 `upload / edit / delete / export / schedule` 之间
的区分,在一个内容工作区里从来没有人真的分开配过。

所以:**只留角色,删掉 9 个权限位与 `WorkspaceMemberPerm` 整张表**。

```
viewer  读内容
editor  读写内容,可以用智能体
admin   editor + 改工作区设置、管成员
owner   admin + 删除/转让工作区
```

少一个概念,少一张表,少 24 处「这条路由该查哪个位」的判断。顺带解掉一个从没起过作用的条件:
`editor` 默认持有 `credentials`,于是 `ensure_instance_admin` 的第二个条件恒真。

**可逆**:真需要逐位配置时再加回来,那时会有真实用例说清楚要哪几位。

### D4 写权限显式化

`ensure_workspace_access` 靠一个只在 ASGI 中间件里绑的 ContextVar 判断该不该查写权限,默认
`"GET"`。它守着 43 条写路由;任何不经 HTTP 的调用(后台线程、队列、定时)拿到的都是默认值 ——
本轮已经在确认卡的批准路径上复现过一次(viewer 在后台线程里批准成功且真的执行了)。

拆成 `ensure_workspace_member`(读)与 `ensure_workspace_role(editor)`(写),逐条标注,改完删掉
那个 ContextVar。

### D5 智能体的权限恒等式

> **智能体能做的 = 行动人能做的 ∩ 这次对话授予的档位**

- **上界**:任何自动放行都必须经过与人工同一个 `authorize_*` 函数。bypass 绕过的是「用户同意」,
  不是「他有没有这个权限」。
- **下界**:三档模式只能收紧,不能放开行动人本来没有的东西。

两侧都用棘轮钉住 —— 下一个人加第二条批准路径时会红。

### D6 归属让确认卡的会话归属变干净

三档权限模式现在靠 `mode_set_by` 记「模式是谁开的」,因为 `AgentSession` 没有主人。有了
`owner_user_id` 之后这个字段可以退场:模式属于会话,会话属于人。

## 3. 迁移(按 [ADR 0006](0006-migrate-instead-of-branching.md):就地迁,读取期不留分支)

1. `users.is_host_owner` → 置给 `created_at` 最早的账号。
2. 四张表补 `owner_user_id` → 回填成**该工作区的 owner**。他是当初建这些东西的人,或者至少是
   现在对它们负责的人。
3. `resource_shares` → 为每一条已存在的记录建一行「共享给它当前所在的工作区」。
   **升级前后行为完全一致**:今天大家都能看见的,升级后仍然看得见;从此以后新建的默认私有。
4. `provider_credentials` → 把 `ProviderProfile` 上的 `api_key` / `oauth_credential` 搬成宿主主人
   名下一行并标共享,然后删掉那三列。
5. `WorkspaceMemberPerm` 整张表删掉,`PERMS` 从代码里去掉。

五步都幂等,读取代码里不出现「有没有这一列」的分支。

## 4. 顺序

| # | 内容 | 影响面 | 前置 |
| --- | --- | --- | --- |
| 1 | `is_host_owner` + `ensure_host_owner` + 宿主能力清单 | 小:一列、一个函数、约 32 处改名 | 无 |
| 2 | 角色即权限:删权限位与整张表 | 中:24 处调用点 + 团队设置页 | 无 |
| 3 | 归属与共享:四张表 + `resource_shares` + 列表过滤 | **大**:触到发布、浏览器池、对话列表、素材可见性 | 1 |
| 4 | 凭据归人(第 3 步的一个实例) | 大:供应商解析、sidecar 下发、OAuth 刷新、额度 | 3 |
| 5 | 写权限显式化(43 条) | 中:机械 | 2 |
| 6 | 智能体恒等式的棘轮 | 小 | 1 |

第 1、2 步互不依赖,都可以先发。**第 3 步之前不要动第 4 步** —— 凭据是归属的一个实例,先有通则
再落特例,否则会写出第二套只服务于供应商的共享机制。

## 5. 被否掉的选项

- **把供应商整个搬到工作区级**:同一个人在三个工作区里要配三次同一把钥匙,而钥匙是他的。
- **给 `ensure_instance_admin` 打补丁(比如"必须在默认工作区里是 admin")**:默认工作区可以被删、
  可以被转让,而且这只是把自助升级的入口换个地方 —— 仍然不是「机器主人」。
- **用配置文件里的 `admin_username` 表示宿主主人**:它在库外,和用户表会各说各话,改一次要重启;
  而这件事本来就该是数据。
- **只修供应商凭据,不动发布账号与浏览器档案**:那是把通则当特例,下一次同类资源出现时会再犯一遍
  (这正是本文第一版做的事)。
- **等到真有团队部署再说**:那时库里已经积着一堆按旧模型建的数据,而迁移难度正比于积压量。
