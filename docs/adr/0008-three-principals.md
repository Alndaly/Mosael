# ADR 0008:设计是多租户,实现是单机

> 状态:**已决定,未实现**。现状盘点见 [PERMISSION_MODEL.md](../PERMISSION_MODEL.md)。
> 本文经过五稿,每一稿都推翻了上一稿的一个前提。前四稿的错误记在 §7 —— 「哪些前提被推翻过」
> 本身是这份文档最有用的部分。

## 0. 前提

Mosael **是一个多租户产品**:工作区是租户边界,一个后端服务多个人,前端可以指向任意后端。
单机安装不是另一种形态,只是**租户数等于一**的退化情况。

这一句是第五稿才写对的。前四稿里我先后写过「本地优先的桌面应用,应用内权限拦不住机器主人,
对他做校验是演戏」、「有两种部署形态,按更难的那种设计」、「让桌面壳证明自己是本机单用户」——
**这些都是在给一个不该存在的分叉找判据**。判据再精确,分叉本身就是错的。

正确的说法只有一句:**设计是多租户的,而实现里到处假设只有一个人。** 下面每一条都是它的推论。

## 1. 三类归属

承认多租户之后,要回答的是:每一样东西是谁的。答案有三种,而现在的模型只表达得出第三种。

| 归属 | 是什么 | 现状 |
| --- | --- | --- |
| **部署的** | 这个后端实例:网络出口、插件启用、解释器路径 | 用「在任意工作区里是 admin」近似,而工作区可以自助新建 —— 加上开放注册,等于**没有闸**(已跑) |
| **某人的** | 他的身份与他的钱:供应商密钥、发布账号、已登录的浏览器、他的对话、他建的定时任务 | **完全不存在**。这五类全按工作区存,没有一张表有 `user_id`(已核) |
| **大家的** | 一起做的东西:素材、序列、工作流、知识库 | 表达得不错,35 张表按 `workspace_id` 隔开,不是成员一律 404 |

**智能体不是第四种归属**:它以某个人的身份行动,权限必须是那个人的子集(见 D6)。

## 2. 证据

### 2.1 跑出来的

```
# 陌生人 → 服务器上的常驻代码
POST /api/auth/register                  200   ← 注册完全开放
PUT  /api/settings/network               403   ← 此刻还挡得住
POST /api/workspaces                     200   ← 他在自己建的工作区里是 owner
PUT  /api/settings/network               200   ← 通了
POST /api/workflows  {含 code 节点}       200   ← 服务端执行任意 Python
GET  /api/settings/tts                   200   ← 顺带读走解释器路径

# 「实例管理员」是自助的
viewer 改实例级网络设置                   403
他自己新建一个工作区之后再改一次           200

# 供应商 OAuth 凭据对 viewer 明文可读
POST /agent/provider-credentials/{id}/acquire   200,响应里含 access token

# 同事的私人对话可读
GET /api/agent/sessions                  ['owner 的私人对话']
GET /api/agent/sessions/{id}/messages    200

# editor 能用同事登录的账号发帖
owner 登录一个 B 站发布账号               200
editor 列出发布账号                       看得见它
editor 用这个账号发起发布                 200
```

### 2.2 读出来的(没跑)

- **`run_python` 不是沙箱**,它自己的 docstring 就这么写:「子进程隔离 + 超时 + 输出上限,
  但**不是沙箱** —— 里面的 Python 能读写文件系统、发网络请求」。
- **定时任务没有主体**:`ScheduledTask` 有 `workspace_id`、没有创建者,`run_scheduled_task` 建 job
  时不带操作人。所以定时跑的工作流(可含 `code` 节点)是无主体执行,而且删掉那个账号也带不走它。
- **密钥明文落盘**:全仓搜不到任何 `encrypt / cipher / keyring`。
- **43 条写路由靠「当前请求是不是 POST」推断权限**(只在 ASGI 中间件里绑的 ContextVar,默认 GET)。
- **`ensure_instance_admin` 的第二个条件恒真**:它要求「角色 ≥ admin 且持有 perm」,而 editor 默认
  持有除 `members` 外的全部权限位。插件路由传的是 `"edit"`,同样如此。
- **worker 通道假设同机**:worker 的身份是写在数据目录里的进程密钥,而 Electron 侧读的是**自己
  这台机器**的那把。所以远程部署下发布/浏览器自动化要么不可用,要么那些「登录态」实际在服务器上。

## 3. 决定

### D1 部署管理员成为一等概念,并且不可自助

`users.is_deployment_admin`。判据不再是「在某处是 admin」—— 那在开放注册下等于没有判据。

- **引导**:库里一个用户都没有时,第一个注册的账号成为部署管理员(自托管软件的通行做法)。
- **引导之后注册转邀请制**,只能由部署管理员发邀请。想保持开放的部署显式打开
  `MOSAEL_OPEN_REGISTRATION`。
- 只有部署管理员能授予或收回这个身份。

`ensure_instance_admin` 改名 `ensure_deployment_admin` 并改判据。它管的是**真·部署配置**:
网络代理、插件启用、TTS 解释器路径、ASR/TTS 模型下载。

**它不再兼任「谁能在服务器上跑代码」的守门人** —— 那是 D2。

### D2 服务端执行代码是**隔离问题**,不是授权问题

这一条替换掉前几稿的「默认关 + 让桌面壳证明自己是本机」。

多租户产品里,「谁有资格写 `code` 节点」是个错问题。正确的问题是:**任何人写的代码跑起来,
能不能伤到别人。** Dify 的 `dify-sandbox` 就是照这个问题设计的 —— 它的 README 第一句是
「为多租户环境设计,多个用户提交代码执行」,然后用 seccomp 系统调用白名单、`chroot`、非 root
用户、独立沙箱网络(出网走代理容器)把边界画死,主服务通过 HTTP 调一个**独立进程**。
所以在 Dify 里,editor 能写 code 节点 —— 因为写了也伤不到别人。

Mosael 现在反过来:执行器**明确不是沙箱**(见 §2.2),于是只好用角色去挡 —— 而那道角色闸
恰好是自助的。两个问题叠在一起,才有了 §2.1 那条链。

**做法**:把 `run_python` / `code` 节点搬进一个真正的隔离执行器 —— 独立进程或容器、非 root、
根目录换到临时目录、系统调用白名单、**默认无出网**(要出网走显式代理,与 `domain/network.py`
已有的代理配置接上)、内存与时长上限。

隔离到位之后:

- `code` 节点退回成**普通的内容编辑权限**,`ensure_graph_node_privileges` 这道闸可以撤掉 ——
  它本来就是缺沙箱的补丁。
- 「定时任务无主体执行」不再是安全问题(它仍然要有主人,那是 D3 的事,理由是可追溯与停摆)。

**在隔离到位之前**:给它一个部署级开关,默认关。这是**止血,不是设计** —— 文档里必须这么写,
不能让一个开关冒充架构。

### D2 落地之后(2026-08-03)

执行器搬进 `app/domain/sandbox`,按平台选后端,**没有可用后端就拒绝执行**(fail closed)——
「能不能跑代码」由是否真的隔离得住决定,不再由开关决定。那个开关连同 `ensure_graph_node_privileges`
一起撤掉了(`PRIVILEGED_NODE_TYPES` 这个概念也没了):代码跑在隔离里,写它就是普通的内容编辑。

| 后端 | 手段 | 验过 |
| --- | --- | --- |
| `darwin` | `sandbox-exec`:deny 网络 / deny 写盘(除临时目录)/ deny 读 home。内核强制,**子进程继承** | 是 |
| `docker` | `--network=none --read-only --user 65534 --cap-drop ALL --pids-limit --memory` | 是 |
| Linux 原生 | 还没有。装了 docker 走 docker;没装则如实拒绝 | —— |

三条都不继承后端进程的环境变量 —— 那是独立于文件与网络的第三条路,后端环境里有各家模型的密钥。

**已知缺口**:Linux 主机上没装 Docker 时不能跑代码。原生 seccomp 后端(dify-sandbox 那种系统调用
白名单)是下一步;在它到位之前宁可拒绝,也不退回到"没有隔离但照跑"。

### D3 「某人的」东西加上主人,并且默认不共享

五张表加 `owner_user_id`,外加一张共享表:

```
publish_accounts   + owner_user_id      -- 他的 B 站/抖音登录
browser_profiles   + owner_user_id      -- 他已登录的浏览器
agent_sessions     + owner_user_id      -- 他的对话
scheduled_tasks    + owner_user_id      -- 它替谁跑(可追溯;主人失去权限时停摆)
provider_credentials(user_id, profile_id)   -- 新表:他的密钥,从 provider_profiles 搬出来

resource_shares(kind, resource_id, workspace_id, shared_by)   -- 主人显式共享进某个工作区
```

**归属与共享是两件事**,现在被压成了一件:今天「把东西放进工作区」既是存储方式也是共享方式,
于是没有「放进来但仍然是我的」这种状态。分开之后,一条规则覆盖五类资源,不是五个特例。

默认私有,共享是主人的一次显式动作、可以撤回。

> **后续实现修订（2026-09）**：`ProviderProfile` 也归创建它的用户，而非实例。多租户实测表明端点、
> 私有模型目录和账号策略同样是个人连接的一部分；实例级连接会把别人的端点暴露到列表里，还会让默认
> 选择先命中别人的连接。现在先按 `owner_user_id` 选择自己的连接，再装配自己在这条连接上的凭据，
> 不存在部署管理员共享回退。详见 [ADR 0010](0010-provider-contracts-adapters-registry.md) 与权限模型文档。

### D4 角色即权限,删掉权限位矩阵

身份类资源搬出工作区之后,权限位剩下的意义所剩无几:`credentials` 没有对应的能力了(配的是
自己的),`publish` 也是(用的是自己的账号)。而 `upload / edit / delete / export / schedule`
之间的区分从来没人真的分开配过。

**只留四个角色,删掉 9 个权限位与 `WorkspaceMemberPerm` 整张表**:

```
viewer  读内容
editor  读写内容,可以用智能体
admin   editor + 改工作区设置、管成员
owner   admin + 删除/转让工作区
```

少一个概念、少一张表、少 24 处「这条路由该查哪个位」的判断,顺带解掉 §2.2 那个恒真条件。
**可逆**:真需要逐位配置时再加回来,那时会有真实用例说清楚要哪几位。

### D5 写权限显式化

拆成 `ensure_workspace_member`(读)与 `ensure_workspace_role(editor)`(写),逐条标注 43 条路由,
改完删掉那个按请求方法推断的 ContextVar —— 留着它就还会有人依赖它。

### D6 智能体的权限恒等式

> **智能体能做的 = 行动人能做的 ∩ 这次对话授予的档位**

- **上界**:任何自动放行都必须经过与人工同一个 `authorize_*` 函数。bypass 绕过的是「用户同意」,
  不是「他有没有这个权限」。
- **下界**:三档模式只能收紧,不能放开行动人本来没有的东西。

两侧都用棘轮钉住(`tests/test_agent_identity_ratchet.py`):上界钉代码形状 —— `approve_confirmation`
只能由 `authorize_and_approve` 调,别的调用点等于一条不过闸的批准路径;下界跑真实场景 —— 人被移出
工作区之后,他那个开着 bypass 的会话做不了决定。

**`mode_set_by` 不能退场**(这一条推翻本 ADR 早先的说法):当时的理由是「模式属于会话,会话属于人」。
但会话可以被共享(D3),共享之后别的成员也能改模式 —— 那时"谁开的"与"谁的会话"是两个人。模式是
一次**授权动作**,只对做出授权的那个人生效;合并两列等于把一个人的授权悄悄转给另一个人。

## 4. 迁移(按 [ADR 0006](0006-migrate-instead-of-branching.md):就地迁,读取期不留分支)

1. `users.is_deployment_admin` → 置给 `created_at` 最早的账号;注册随即转邀请制。
2. 五张表补 `owner_user_id` → 回填成该工作区的 owner。
3. `resource_shares` → 为每条已存在的记录建一行「共享给它当前所在的工作区」。
   **升级前后行为完全一致**:今天大家能看见的仍然看得见;从此新建的默认私有。
4. `provider_credentials` → 把 `ProviderProfile` 上的 `api_key` / `oauth_credential` 搬成部署管理员
   名下一行并删掉秘密列；后续迁移再给连接补 `owner_user_id`，旧连接归部署管理员，新连接归创建者。
5. `WorkspaceMemberPerm` 整张表删掉,`PERMS` 从代码里去掉。

五步都幂等,读取代码里不出现「有没有这一列」的分支。

## 5. 顺序

| # | 内容 | 影响面 | 前置 |
| --- | --- | --- | --- |
| 0 | 注册转邀请制 + 服务端执行代码默认关(**止血**) | 小 | 无 |
| 1 | `is_deployment_admin` + `ensure_deployment_admin` + 部署能力清单 | 小 | 无 |
| 2 | 角色即权限:删权限位与整张表 | 中:24 处调用点 + 团队设置页 | 无 |
| 3 | 归属与共享:五张表 + `resource_shares` + 列表过滤 | **大** | 1 |
| 4 | 凭据归人(第 3 步的一个实例) | 大:供应商解析、sidecar 下发、OAuth 刷新、额度 | 3 |
| 5 | **隔离执行器**(D2) | **大**:独立进程/容器、seccomp、chroot、出网策略 | 无 | ✅ 已完成(见 D2 落地) |
| 6 | 写权限显式化(66 条) | 中:机械 | 2 | ✅ 已完成 |
| 7 | 智能体恒等式的棘轮 | 小 | 1 | ✅ 已完成 |

第 0 步先发:它掐断 §2.1 那条链的第一环和最后一环,不依赖其余任何一步。
第 5 步是唯一真正解决代码执行的那一步,**它到位之后第 0 步的那个开关可以撤掉**。

## 6. 被否掉的选项

- **用部署形态(本机 / 共享)做设计轴**。前四稿的错误:产品本身是多租户的,单机只是租户数等于一。
  给一个不该存在的分叉找判据,判据再精确也没用。
- **按绑定地址自动决定能不能跑代码**。「绑 127.0.0.1 + 反向代理对外」是常见部署,自动判据会在
  那里选中最危险的默认值,而后端看不见自己前面站着谁。
- **让桌面壳证明自己是本机单用户**(第四稿的做法)。同上 —— 它比绑定地址精确,但它精确地回答了
  一个错问题。
- **靠角色挡住代码执行,不做沙箱**。那是拿授权去补隔离的缺口,而这个缺口的后果不在这个应用里。
- **只修供应商凭据,不动发布账号与浏览器档案**。那是把通则当特例(第二稿的错误)。
- **把供应商整个搬到工作区级**。同一个人在三个工作区里要配三次同一把钥匙,而钥匙是他的。
- **用配置文件里的 `admin_username` 表示部署管理员**。它在库外,和用户表会各说各话。
  (但**开关**类的东西 —— 注册是否开放、沙箱到位前能不能跑代码 —— 留在配置里是对的:
  它们是部署的属性,不是某个人的属性。)

## 7. 五稿之间改过什么

| 稿 | 当时的前提 | 被什么推翻 |
| --- | --- | --- |
| 一 | 「凭据归人」是供应商的一条修复 | 发布账号、浏览器档案、对话是同一类东西 —— 通则,不是特例 |
| 二 | 给自己加了「不动角色、不做多租户」这类限制 | 这些不是从现实推出来的,是从「少改一点」推出来的 |
| 三 | 后端总在用户自己机器上 | 应用支持分布式部署 |
| 四 | 有两种部署形态,让桌面壳证明自己是本机 | 产品本身就是多租户的,这个分叉不该存在 |
| 五 | —— | 服务端执行代码是隔离问题,不是授权问题(参照 Dify 的 sandbox) |
