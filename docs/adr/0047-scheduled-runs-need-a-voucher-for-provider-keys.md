# ADR 0047:定时任务的担保人 —— 主人的 AI 钥匙和额度,也要有人为「被执行的那一版」担保

## Status

Accepted — 2026-10-09。草稿 2026-10-08(体检 SEC-2 后半);六个待拍板点由**维护者 2026-10-09 按推荐拍板**,落成下面的
决定 1–6(体检编号 D6–D11)。实现与本篇同一次提交,见文末「实现记录」。

直接修法已经先做了(体检第一批,`fix(scheduler)`):定时任务的改、启停、删、重置触发密钥、立即运行只许主人
(`ensure_manageable`);webhook 触发密钥只存哈希、原文只给主人看一次。本篇处理剩下的那一半:**任务本身锁住了,任务绑着的
工作流还是工作区内容**。

## Context

### 一次定时运行替谁花钱

| 东西 | 定时 / webhook 运行里用谁的 | 此前有没有担保人检查(PERMISSION_MODEL §3.8) |
| --- | --- | --- |
| 私有发布账号、浏览器档案、本机文件 | 任务主人的 | **有**:被执行的每一版图,至少一个担保人(作者或认可过这一版的人)自己也用得了 |
| AI 供应商连接(钥匙)、默认模型、额度 | 任务主人的(生成、对话、配音等按「跑的人」解析) | **没有**:只看跑的人是谁 |
| 插件连接(ComfyUI 等,可能是付费 GPU / 云) | 任务主人的 | 没有 |
| 免费的内置引擎(Edge 语音、本机 ffmpeg) | — | 不需要(不花钱、不用私人凭据) |

§3.8 当初要关的是「同事改了主人的图,到点一跑,就以主人的授权用主人的东西」,只对私有身份关了。AI 钥匙和额度同样是主人
个人的(连接归人,ADR 0008 D3),同样会被「被执行的那一版图」决定怎么花,却只看跑的人。

### 风险是什么(不写可直接照做的步骤)

工作流是工作区内容,编辑者能改;被调用的子流程同样。主人的定时任务绑着一张工作流,到点按**当前那一版**跑、用主人的钥匙和
额度。于是能改那张图(或它调用的子流程)的人,就能决定主人的钥匙和额度下一次花在什么上 —— 花多少、调哪家、生成什么内容、
调用记在主人的连接上。第一批的修法只让「改任务」只归主人,没有改变「图归工作区」。

单机部署不受影响:作者、主人、跑的人永远是同一个人。

### 已有的机制可以复用

- 一次运行的授权已经是两半的交集(`domain/authority`、`workflows.authority.current_authority`):跑的人 + 每一版的担保人,
  沿 job 父链收集,子流程那一层也算。
- 挡下来时的失败现场带 `details.attest`,运行历史和定时任务运行记录上已有「认可这一版」(不改图、不增版)。
- 运行前检查(`engine.check_runnable` → `run_preflights`)能在开跑之前说「跑不起来」,不花钱。

## Decision

### 1. 判据对所有运行一样;点运行即认可(D6)

一次运行要用**属于某人的**供应商连接或插件连接时,判据和 §3.8 一样:跑的人是这条连接的主人,**并且**被执行的每一版图都有
一个担保人是这条连接的主人。连接只归一个人、只有主人用得了,所以落到实处就是:**主人的定时任务只在主人自己存的、或主人认可
过的那一版上花主人的钥匙。**

判据不分运行的来路。但人点了「运行」(编辑器)、「立即运行」(定时任务页),或亲手点了智能体「运行工作流」卡上的同意,
他就在现场 —— **点的那一下记成他对当前这一版的认可**。所以有人看着的运行零摩擦,实际被挡下的只有无人看着的运行:到点的
定时任务、webhook、智能体自动放行的卡。

认可的只是**眼前这张图的当前版**。它调用的子流程是别人改过、他还没认可的那一版,照样停下来请他认可那一版 —— 他点运行时
看见的不是子流程的图。

### 2. 什么算「花主人的钱」(D7)

解析任何一条**属于某人的**供应商连接或插件连接都算 —— 插件背后可能是付费 GPU / 云,带着他的凭据。免费的内置能力(Edge 语音、
本机 ffmpeg、本地渲染)不经过连接,不算。不属于任何人的连接(没有主人)没有谁的钱可花,不判。

### 3. 开跑前查为主,执行时的闸兜底(D8)

- **开跑前**(`engine.start_workflow_job`):这一次运行(连同字面量调用的子流程,顺下去)里有会用到某人连接的节点时,先查
  每一版有没有跑的人担保;过不了就不开跑、一分钱不花,失败现场带 `details.attest`。哪些节点会用到连接,**声明在节点自己身上**
  (`"spends": True/False`,和 `"external"` 同一种做法,棘轮要求每个节点都写);插件节点一律算。判的是节点类型,所以是保守的:
  配音节点选了免费的内置引擎也算。
- **执行时**(`domain/authority.ensure_vouched_to_spend`):连接在执行器里散在生成、对话、配音、翻译、插件调用各处解析,而且
  隔着好几层(生成任务是工作流任务的子任务)。所以这道闸不靠调用方把授权一路传下去,而是放在**解析连接的那一处**
  (`providers.credentials.resolve_connection`)和**插件干活的两条路**(`plugins.tools.invoke` / `invoke_host`),自己从任务
  上下文里取这次运行的授权。运行中途才定下来的连接(子流程名字写成引用、按参数选的模型)在这里拦。

这一条**不**放进「图跑不跑得起来」(`check_runnable`):后者在定时任务启用、到点触发之前都问,不过就停用任务;而「这一版等主人
认可」不是跑不起来,任务该照常到点、每次记一条带「认可这一版」的失败。

### 4. 认可按修订,一次对这一版所有连接有效(D9)

和 §3.8 同一张认可表(`workflow_revision_attestations`)。认可一版,对这一版要用的所有连接都有效;不按连接分别认可。

### 5. 改图只提醒、不拦(D10)

改图是工作区内容的正常操作,不拦。有人存了一版**被别人的定时任务绑着**的工作流(或它调用的子流程)时:

- 给任务主人发一条通知(「定时任务等你确认工作流的新版本」,点开到定时任务页);同一个任务还有一条没读的就不再发 ——
  编辑器是自动保存的,改一处就是一版;
- 任务上挂「待你确认」:列表里一眼看得见,详情里说清是哪条工作流的哪一版,主人就地点「认可这一版」;别人看到的是「待主人
  确认」,没有认可按钮(他认可不算数,花的不是他的钱);
- 编辑器顶上提醒改图的人:「A 的定时任务用着这张图,改过的这一版要 A 认可之后,它到点才会接着用 A 的 AI 连接」;主人自己打开
  这张图时同一处给「认可这一版」。

### 6. 升级时补认可(D11)

当前那一版不是主人存的、主人也没认可过的任务,升级后第一次到点就会停下 —— 而它们此前就是这样在跑。所以迁移给每个工作流
任务的主人,对绑着的那张图的当前版、以及它字面量调用的子流程的当前版(顺下去),各记一条认可。以后别人再改,照第 5 条提醒。
一次性迁移,数据库版本号随之加一。

## 否掉的备选

- **任务钉死一版图**(建任务时记下修订号,之后只跑那一版):语义变了(「绑定工作流」不再跟着工作流走),主人每次改图都要回来
  重新钉;子流程也得一起钉。比认可更麻烦,保护的东西一样。
- **绑着定时任务的工作流只许主人改**:协作场景里工作流常常是大家一起改的;而且子流程、模板复制出来的图都要跟着锁,牵连太广。
- **定时运行改记在最后改图的人头上**:主人的意图(「每天替我跑这个」)丢了,改图的人也未必有钥匙;花钱的主体变得不可预期。
- **工作区级共享连接 + 预算**:是更大的一件事(连接归属模型要变),不该为这一处引进;本篇的交集判据将来对共享连接同样成立。
- **只对定时 / webhook 运行生效**:实现少一点,但智能体自动放行跑的工作流也会花主人的钱,漏了一类(D6 的备选)。
- **只算有计价的远端调用**:要先知道每次调用要不要钱,做不到事前判断(D7 的备选)。
- **只在执行器里查**:会在花了一部分钱之后才停下(D8 的备选)。
- **按连接分别认可**:太碎(D9 的备选)。
- **升级时不补认可、只通知**:更严,但第一天就会有一批任务停下(D11 的备选)。

## Consequences

- 团队部署里,别人改过的工作流会让主人的定时任务停下,直到主人认可 —— 这是有意的摩擦,换来「我的钥匙只花在我认可的图上」。
  通知、「待你确认」和编辑器里的提醒把这个摩擦提前到改图的时候,而不是失败之后。
- 单机部署零变化。
- 新节点必须声明 `"spends"`;漏写测试就红。声明是保守的(按类型),执行时的闸只拦真用到连接的那一刻。
- 被挡下来的那一版不会在主人的连接上留下用量事件。
- 点运行即认可也作用于 §3.8 的私有身份:有人看着的运行不再被「这一版要你认可」挡下。

## 实现记录(2026-10-09)

- 判据与闸:`domain/authority.ensure_vouched_to_spend`(`SpendNotVouched`,`spendErr_notVouched`)。「这次运行的授权」由组装根
  交给它(`use_run_authority(workflows.authority.current_authority)`,见 `app.main._wire_seams`)—— 供应商、插件两个域不认识工作流。
- 开跑前:`workflows.engine.unvouched_spend`,在 `start_workflow_job` 里问(`wfErr_spendNotVouched`);挂在哪条运行底下由
  `workflows.authority.run_authority` 从任务父链收(定时任务复用的包装任务还没钉修订,从它的上一层问起)。节点声明见
  `workflows/node_types.py` 的 `"spends"`,`graph_rules.SPENDING_NODE_TYPES` / `spending_nodes_in_graph`。
- 失败现场:`jobs.failure_payload`(原 `engine._failure_payload` 挪来共用);定时任务派发时停下的把 `attest` 写进运行记录;
  子任务(生成、配音)撞上闸时由任务总线的兜底把 `details` 留在子任务上,工作流照旧转上去;`call_workflow` 开不了子流程时
  带着子流程那一句的 `attest`。
- 点运行即认可:`workflows.revisions.attest_current_revision`,在编辑器的运行路由、`scheduler.use_cases.run_now`(经
  `scheduler.approvals.attest_bound_workflow`)、智能体卡人点同意时(`decision_mode == "manual"`)调。
- 提醒:`workflows.revisions.on_saved`(组装根登记 `scheduler.approvals.remind_owners`,机械改写不通知);任务上的
  `awaiting_approval`(`ScheduledTaskOut`);编辑器读 `GET /workflows/{id}/awaiting-approvals`。
- 迁移:`migrate-scheduled-tasks-vouch-for-what-they-run`,`DATABASE_SCHEMA_VERSION` 12 → 13(落在 ADR 0049 的 12 之后)。
