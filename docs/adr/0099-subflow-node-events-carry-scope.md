# 0099 内嵌子图节点事件带作用域

- 状态：已采纳
- 日期：2026-11-12

## 背景

循环体与内嵌 `subgraph` 和外层工作流跑同一套引擎，但它们的 `run_graph` 没有自己的 job：

- `node_event` 只在 `has_job` 为真时发事件，子图里的节点因此完全没有 started / finished / failed；
- 前端 `toSteps` 只按裸 `node_id` 归并，即便事件到了，也无法区分「同一个节点在哪个容器、哪一轮循环」；
- 结果就是子画布只能看到容器节点的一条进度条，体里的节点一直不亮，检查器里也拿不到体节点这一步的状态。

## 决策

子图内节点的事件记到**外层 job** 上，并带一个 `scope`：

- `scope` 是容器路径 + 循环轮次，例如 `loop-1/#0`、`outer/#1/inner/#0`；
- 顶层节点事件的形状不变，不带 `scope`；
- 前端以 `scope/node_id` 作为归并键；`stepsAtScope` 把当前画布路径与容器 id 对齐、跳过 `#N`
  轮次，同一个体节点在多轮里出现时按「失败 > 被停 > 运行中 > 跳过 > 完成」取一个状态。

节点名称取子图自己的 `name`，没有名字时退回节点类型；前端仍有完整注册表，不依赖事件里的
`name_key` 做显示。

## 后果

- 子画布、边着色、节点角标、NodeInspector 共用同一份按作用域归并后的状态。
- 循环多轮会多出事件行；这是执行历史的一部分，且只写在外层 job 上，不新增表或 job。
- 旧记录没有 `scope`，仍按原来的顶层归并方式读取，不需要迁移。
- 子图事件写入使用 `unit_of_work()`，不把内层执行器的连接生命周期带进外层事务。

## 验证

- `test_内嵌子图的节点事件带作用域_子画布据此显示节点运行态`：纯 template 循环体跑一次，
  确认事件带 `loop/#0` 作用域。
- `runSteps.test.ts`：带 scope 的事件按 `scope/node_id` 归并；多轮状态按 rank 选择。
- 前端全量测试通过。
