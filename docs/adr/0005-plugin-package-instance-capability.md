# 插件拆成「包 / 实例 / 能力」三层,能力默认不暴露

一个插件**包**(磁盘目录 + manifest)可以有多个**实例**(一次具体接入:一组配置 + 一组凭据 + 一个显示名),每个实例暴露哪些**能力**(工具)由用户逐项决定,默认一个都不暴露。配置(有类型、有选项、明文)与凭据(密文、掩码回显)是两张表、两种控件;显示名由模板从配置生成,不写死在 manifest 里。工作流节点类型绑**包**(`plugin.<包id>.<工具名>`),用哪个实例由节点上的 `instance_id` 决定。

**这是在修三个已经发生的故障**:

1. **名字与实际连接不符**。TikHub 的平台是一个"凭据"(`TIKHUB_PLATFORM=bilibili`),而包名写死成「TikHub 抖音数据」—— 节点面板上于是出现「bilibili_web_fetch_one_video / TikHub 抖音数据」。身份来自配置,名字却是常量。
2. **41 个工具全量涌入**。MCP 服务报什么就全接什么,节点面板和智能体工具表被 `bilibili_web_fetch_*` 淹没。这两处都是注意力稀缺的地方:面板要人从四十行里找一行,工具表让每轮对话为四十条描述付 token 并挤占模型的选择权。
3. **一个包只能接一个端点**。要同时用 bilibili 和 douyin,得把目录复制一份、手改 id —— 而这两者本来就该是同一个包的两次接入。

**Considered options**:

- **保持一行 Plugin = 一次接入,只修名字和默认暴露** — 拒绝:能修掉 1 和 2,修不掉 3,而「复制目录改 id」会把同一个包的两份副本变成两个各自升级的东西。
- **把平台做成工具参数而非连接配置**(一个实例连所有平台) — 拒绝:MCP 的端点就是按平台分的,一个会话对一个端点,这是协议的形状不是我们的选择。
- **能力默认全暴露,让用户去关** — 拒绝:默认值就是实际行为。四十个工具里挑出该关的三十七个,没有人会做。与权限 deny-by-default 同一个判断。
- **节点类型绑实例**(`plugin.<实例id>.<工具>`) — 拒绝:工作流会被导出到别的机器,而实例是本机事实;节点类型必须跨机器稳定。绑包、把实例放进节点 config,导出后缺的是"连接"而不是"节点类型"。
